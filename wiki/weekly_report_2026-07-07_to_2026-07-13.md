## 一、本周目标

1. 审计 64 核 stop_machine/IPI 结论，避免继续沿“58 个 hart MSIP 线永久断开”的错误解释投入。

3. 逐层验证 P3 板上链路：PDI/DONE、debug hub、UART、DDR、SPI-SD/GPT、OpenSBI、Linux early console。
4. 对本周暴露的 2 核 OpenSBI 入口问题做 A/B 控制，生成可复现的修复镜像并完成 SD 写后回读。
5. 对 Linux 早期停止继续定位，给出下一轮最便宜、证据边界清楚的控制实验。

## 二、本周核心成果（一句话）

**Build 73 2 核板级链路已从 bootrom 打通到 OpenSBI v1.8 和 Linux 6.6 early console；本周证实并修复了 CSR 0x701 关闭 D-cache 导致 OpenSBI `sbi_hart_init()` 后续路径无法完成的问题，以及 OpenSBI mtimer 注册顺序导致的 1 MHz/234375 Hz 频率错误；当前剩余阻塞已后移到 Linux `setup_vm_final()` 附近，Build 73 的 1 GiB/2 GiB CVA6 DDR aperture 不匹配是已确认配置 bug 和高置信候选，但还需要 `mem=1G` 或 corrected-PDI A/B 闭环。**

## 四、本周新问题与根因

### A. “58 个 hart 收不到 MSIP”是过度解读，不是已证实根因

- **现象**：上一阶段 stop_machine 卡死时，只有 `{0,1,3,4,11,12}` 等少数 CPU 打出 soft-lockup，曾被写成“64 online 但只有 6 个响应 IPI”。
- **纠正后的判断**：这个结论过度解读。Linux 能打印 `smp: Brought up 1 node, 64 CPUs`，说明所有 secondary hart 都已经经由 OpenSBI HSM 的 MSIP wakeup 从 `wfi()` 拉起过；永久性 MSIP 线断开不成立。
- **机理**：soft-lockup 是每 CPU watchdog。没有 soft-lockup 输出，可能是 CPU idle、timer IRQ 已死、卡在别处，不能直接推出“没有收到 IPI”。stop_machine 还依赖 `multi_stop_data` 共享状态、S-mode/MMU、timer 和 IPI 的组合路径，不只是 CLINT MSIP 写入。
- **修复/验证**：本周转向两个更贴近真实失败的方向：一是对 L1.5 monitor fail 分支加自报告，二是新增 `coh_stopmachine.c` 模拟 leader plain-store + follower tight-spin 的 `multi_cpu_stop` 状态推进模式。
- **证据边界**：这不是说 stop_machine 问题已经解决，而是撤销“58 根 MSIP 线坏了”的根因表述。后续应看共享状态可见性、MMU/TLB、真实 DDR/CDC/timer 并发，而不是只查静态 MSIP offset。

### B. 64 核纯功能级 coherence/shared-state race 被显著削弱

- **现象**：旧 `coh_ipi64` 的一次 L1.5 monitor fail 曾被当作强线索，但后续三次 progress-only sweep 已通过，本周需要判断是否继续烧时间追这个仿真窗口。
- **当前判断**：在 Verilator 5.046 的 8x8 模型里，`coh_2core`、`coh_64core`、`coh_ipi64 x4`、`coh_stopmachine` 全部 PASS，且无新 monitor fail。纯 L1/L2/NoC 功能级 coherence 逻辑错误已不是主导候选。
- **机理**：`coh_stopmachine` 是本周最关键的负例：它直接模拟 stop_machine 的共享状态推进和 tight-spin 读取。如果这个最贴近访问模式的 bare-metal 诊断都过，而板上 Linux 仍挂，则差异更可能来自仿真不覆盖的层：真实 DDR/MIG/CDC、S-mode MMU/TLB、timer+IPI+工作负载并发。
- **修复/验证**：commit `d941c89` 增加 monitor 自报告和 `coh_stopmachine.c`；随后 `coh_ipi64` 第四次 PASS（`main_time=53.7M`，54 分钟）和 `coh_stopmachine` PASS（`main_time=44M`，43 分钟，8 轮）。
- **证据边界**：不能写成“硬件没有 coherence/ordering 问题”。只能说本地 RTL 功能仿真没有复现，后续优先板级证据。

### C. 2x1 Build 72/73 生成流踩到三个可复用坑

- **现象**：2x1 构建初期出现 stale PyHP 输出与工具路径问题，Build 73 实现完成后 Vivado 又在 PDI 写出前消失。
- **根因**：
  - P3 的 io_xbar 是九设备配置，旧八口 `chipset_impl.tmp.v` 会导致 `dataIn_8` 不存在。
  - Windows Vivado 侧不能执行 WSL 的 `pyhp.py`，所以不能依赖 Windows Tcl 运行时即时生成所有 tmp。
  - Build 52-derived flow 的强制生成清单不完整，后面又暴露出 `tile.tmp.v` 可被 mtime 复用。
- **修复/验证**：Build 72 先在 Linux 侧生成完整 target-context tmp 集合，成功出 PDI，时序全过。Build 73 从 `p3_top_physopt.dcp` 恢复 `route_design` 和 `write_device_image`，避免 4 小时全量重跑，约 30 分钟恢复出 PDI/LTX。
- **结论**：2x1 PDI 构建链路可用，但必须把 PyHP 输出的 device-map 上下文纳入 preflight，尤其是后面发现的 `tile.tmp.v` DDR aperture。

### D. 2 核 SD-read hang 的根因是卡未插紧，不是 2x1 RTL

- **现象**：Build 72 和 Build 73 起初都停在 `copying block 0 of 1 blocks (0 %)`，也就是读取 GPT LBA1 的第一笔真实 SD data read。
- **根因**：SD 卡在 FPGA push-push 插槽里未完全插紧。重新插紧后，同一 Build 73 PDI 和同一类镜像通过 GPT signature、P3OS/BI64 header、OpenSBI/Linux/DTB/initrd 四组件复制。
- **机理**：bootrom 的 `init_sd()` 只打印并返回，不真正验证卡存在；第一笔 `CMD17`/SD data read 才会触发硬件路径。卡未响应时 SD 控制器等待，AXI/NoC load 永不返回，而设计没有请求超时，所以现象像 RTL 死锁。
- **修复/验证**：物理 reseat 后同一诊断 bootrom 直接越过旧 stop 点，证明 UART、DDR、SPI-SD 控制器、io_xbar 和 NoC response routing 在 2x1 下都能工作。
- **教训**：后续 SD 路径 debug 前，先做卡座物理确认和完整 bootrom 读 trace；不要从 `init_sd OK` 推出卡或 SD data path 已经验证。

### E. CSR 0x701 关闭 Ariane D-cache 会阻断 OpenSBI `sbi_hart_init()` 后续执行

- **现象**：CSR-enabled probe 镜像完整通过 bootrom 复制并跳到 `0x80000000`，OpenSBI raw marker 停在 `II[SHDMW`；30 秒后仍无 `R`。`W` 在 `wake_coldboot_harts()` 后，`R` 只在 `sbi_hart_init()` 返回后打印。
- **根因**：`csrw 0x701, zero` 写的是 Ariane 的 D-cache enable 控制位，写 0 会关闭 L1 D-cache。两核对照镜像唯一关键差异是去掉这条写入，结果继续打印 `II[SHDMWRTEPB`、OpenSBI v1.8 和 Linux early console。历史 64 核 dbg23 也表现为加入该写入后 OpenSBI 跳转后 30 分钟无 banner。因此本周最终结论是：P3 上这条 D-cache-disable 路径对所有 hart count 都是死路。
- **机理**：正常完整设计里，关 D-cache 不应破坏架构正确性，最多变慢；但在 Ariane write-through D-cache + OpenPiton L1.5/NoC 集成里，这会把早期栈、BSS、PMP/trap 初始化等 DDR 访问从已验证的 L1 cacheable 路径改到 non-cacheable/pass-through 路径。实板证明该路径在 OpenSBI 早期失去 forward progress。精确是哪一笔 transaction、哪个状态机或 ordering 条件失败，本周没有 transaction-level ILA 证据，不能进一步命名为某个具体 RTL 子块根因。
- **修复/验证**：最终修复是从 clean-package P3 OpenSBI patch 中移除 CSR 0x701 写入，不再按 hart count gate。commit `cac6e30` 落地后生成 all-hart L1-enabled firmware（SHA `ba46ef13...`）和 256 MiB SD 镜像（SHA `bf8fca762d7cd9a599850e1d795fde664edcdd0cc2ec869964d413ebbc0360ff`），远端写卡并完整 256 MiB 回读匹配。Build 73 随后板上 `DONE bit: HIGH`、debug hub `0x3ffc0000000`、4 个 ILA 枚举，UART 到 OpenSBI 和 Linux early。
- **结论**：CSR 0x701 已闭环为 OpenSBI 入口 gate 的根因；但其底层微结构 failure mode 仍是待查问题。

### F. OpenSBI mtimer 报告 1 MHz 是长期注册顺序 bug

- **现象**：Build 73 OpenSBI banner 报告 `Platform Timer Device : aclint-mtimer @ 1000000Hz`，而 P3 硬件和 DTB 都是 `30 MHz / 128 = 234375 Hz`。
- **根因**：OpenPiton platform data 里有 1 MHz fallback。原流程先在 `sbi_timer_init()` 中注册并复制 fallback 到全局 timer device，之后 `platform_early_init` 才解析 DTB `timebase-frequency`，因此更新太晚，banner 和 OpenSBI delay/timeout helper 仍使用 1 MHz。
- **机理**：SBI TIME 给 Linux 设置的是绝对 `mtimecmp` 值，本身不按 banner 频率缩放，所以这不直接解释 reserved-memory 后的 Linux early stop；但 OpenSBI 内部基于频率换算的 delay/timeout 会错 `1000000 / 234375 = 64/15` 倍，属于必须修的真实平台 bug。
- **修复/验证**：commit `adcb11f` 把 DTB 频率解析移动到 OpenPiton timer callback，在 `aclint_mtimer_cold_init()` 前更新 `mtimer.mtime_freq`，并让准备脚本拒绝 stale work tree。timerfix firmware SHA `69d3549f...`，timerfix image SHA `c420d81d...f55e`。完整 SD readback 匹配后，板上 UART 明确打印 `aclint-mtimer @ 234375Hz`。
- **证据边界**：这修复了 OpenSBI timer 注册错误；它不是当前 Linux early stop 的充分解释，因为保留的旧 64 核日志在同样 1 MHz mismatch 下已经越过 OpenSBI/Linux 早期并进入更晚阶段。

### G. Linux reserved-memory 后停止：Build 73 DDR aperture mismatch 是已确认配置 bug

- **现象**：timerfix 后，Linux 打到 early console 和 reserved-memory 两行后 91 秒无增长。随后不复位捕获 ILA：core 反复完成 8-byte load 到物理 `0xffe5e000`，DDR 侧为 `0x7fe5e000`；没有 L1.5/DDR error，heartbeat 仍活动。
- **根因或当前判断**：Build 73 self-contained snapshot 的 `tile.tmp.v` 把 CVA6 `ExecuteRegionLength` 和 `CachedRegionLength` 都设成 `0x40000000`，即只把 `0x80000000..0xbfffffff` 当作 executable/cacheable RAM；但 P3 device map 和 DTB 声明 2 GiB，即 `0x80000000..0xffffffff`。这是确定的配置错误，也是当前 Linux early stop 的高置信候选。
- **机理**：reserved-memory 后 Linux 进入 `setup_vm_final()`、final page table 构建、`satp` 切换和 TLB flush 窗口，期间可能访问高端 memblock/page-table 区域。观察到的 `0xffe5e000` 正落在 CVA6 stale 1 GiB aperture 之外，却仍在 DTB 声明的 2 GiB RAM 内，和症状相符。
- **修复/验证计划**：短路径是保持 Build 73 PDI 不变，写入只改 bootargs 的 `mem=1G` SD 镜像作为 A/B 控制；长期修复是重新生成 `tile.tmp.v`，在 snapshot preflight 中强制检查两个 length 都为 `0x80000000` 后重新出 corrected PDI。
- **证据边界**：DDR aperture mismatch 已经是 confirmed bug；但“它就是 Linux early stop 的唯一根因”还未闭环。即使 `mem=1G` 成功，也只能证明 upper-GiB use 是触发条件，仍需要 corrected-PDI 对照完成归因。

## 五、方法论与纠偏

1. **先证据审计再继续 debug**：本周最重要的纠偏不是新代码，而是撤销“58 个 hart 永久收不到 MSIP”的过度结论，避免把后续工作压到错误假设上。
2. **用最小对照替代泛化推断**：CSR 0x701 不是靠静态猜测闭环，而是靠同 PDI、同板、同 bootrom、只去掉 CSR 写入的 SD 镜像 A/B 控制闭环。
3. **板级分层证据不跳步**：PDI DONE、debug hub、ILA 枚举、UART、DDR、SD/GPT、bundle copy、OpenSBI、Linux early，每一层单独确认；0-byte UART 不再被直接解释为 firmware failure。
4. **物理层变量纳入排查**：SD 卡未插紧产生了和 RTL/NoC hang 一样的第一笔 SD read 永不返回现象。本周明确把卡座接触作为 SD debug 的前置 gate。
5. **R1 wiki 同步保持即时**：本周每个非显然根因、纠偏、板测结果都已写入 `wiki/devlog/2026-07.md` 并提交推送；本周报是对这些原子记录的汇总，不替代原始证据。

## 八、对 P0-P4 路线图的影响

- **P0/P1 基线**：Build 66/67 的历史板级价值仍在；本周新增的是 OpenSBI/Linux-6.6 这条新软件栈在 2 核 Build 73 上已经越过 bootrom 和 OpenSBI gate。
- **P2/P3（2 核到 64 核扩展）**：2x1 不再被 SD RTL 假问题阻塞，可以作为最小多核 PDI/SD/ILA 对照平台。64 核 stop_machine 的“永久 MSIP 断线”叙述已撤销，后续应重点查真实硬件时序/MMU/TLB/CDC 或 barrier 覆盖缺口。
- **P4（千核目标）**：本周暴露的是可扩展工程纪律问题：PyHP 生成上下文必须可审计，OpenSBI platform fallback 不能在注册后才被 DTB 覆盖，硬件 debug 不能依赖未验证的 cache-disable path。否则这些问题在更大规模会被放大成难以复现的静默 hang。
