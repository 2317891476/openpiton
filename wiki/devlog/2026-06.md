## 2026-06-01 -- P3 Build 52 SD card-detect mask implemented

- Added Build 52 as the direct follow-up to the Build 51 hardware result. Build 52 keeps the original Xilinx AXI16550 UART path, the same native OpenPiton SD controller, the same SD pins/clocks, the same no-stack SD-probe bootrom, and the same four BD-owned ILA shape.
- Added `P3_SD_IGNORE_CARD_DETECT_RESET` in `piton_sd_top`. Under this build-only macro, raw `sd_cd` is still probed, but it no longer contributes to the SD block's internal reset; `rst` becomes `sys_rst` for the SD controller/init path.
- Added Build 52 scripts using the short Windows path `D:/p3b52` by default: build/create/prepare/capture/decode/rebuild scripts publish `p3_top_build52_sd_cd_mask.pdi/.ltx` under `huaprop3_build52_sd_cd_mask/debug_build`.
- Expected decision point: if Build 52 shows internal SD reset released and SD clock/CMD/Wishbone ack activity, the current root cause is the P3 card-detect polarity/connection path. If reset releases but SD init still stalls, the next target is SD clock generation, OpenCores Wishbone ack, or CMD/DAT physical response.

## 2026-06-01 -- P3 Build 51 hardware result: SD card-detect holds native SD reset

- Build 51 completed from `D:/p3b51` and published `huaprop3_build51_sd_init_debug/debug_build/p3_top_build51_sd_init_debug.pdi` and `.ltx`. Top synthesis, placement, route, and `write_device_image` completed with 0 errors; route status had 0 failed nets and the post-route estimate was positive (`WNS=9.131 ns`, `WHS=0.006 ns`).
- Programming through `hw_server 100.93.77.36:3121` and XVC `202.197.4.99:2540` succeeded with `DONE bit: HIGH`. The debug hub refreshed through `PMC_AXI_NOC0` at `0x3ffc0000000`, and all four BD-owned ILAs exported CSV.
- Decode reported `top_status=0xff00`, `core_seen=0x7fff`, SD-init seen bits `0x00cb`, and DDR seen bits `0x8001`. The SD-init live bus was `0x0000280001f01066`.
- The decisive SD-init bits are `sd_cd=1`, aggregated SD reset `rst=1`, `init_done=0`, `wb_stb=1`, `wb_we=1`, `wb_ack=0`, `sd_clk_toggle=0`, and no CMD/DAT output-enable activity. Because `piton_sd_top` defines its internal reset as `sys_rst | sd_cd`, the observed high card-detect input holds the SD controller and init FSM in reset.
- This explains the Build 49/50 symptom `buf_sd_noc2_valid=1` with `sd_buf_noc2_ready=0`: the SD request path cannot accept CPU requests until `init_done` rises, and `init_done` cannot rise while the SD block is reset by card-detect. The next build should mask `sd_cd` out of the internal reset while still probing the raw card-detect input.
