## 2026-06-26 -- ROOT CAUSE of 64-core coherency race: Ariane L1↔L1.5 invalidate path DISABLED by design (all boards)

### Static RTL analysis confirmed: L2 directory + NoC coherence fully implemented, but L1 D-cache cannot receive invalidation

**The coherency path and where it breaks:**

```
Tile A writes addr X
 → L2 directory updates sharer bitmap, sends invalidate via NoC3
 → NoC delivers to Tile B's transducer
 → ccx_l15_transducer.v:55 outputs transducer_l15_invalidate_cacheline = 1 ✓
 → l15_wrap.v:42 receives transducer_l15_invalidate_cacheline ✓
 → tile.tmp.v:259,753,848,919 wires the signal correctly ✓
 → wt_l15_adapter.sv:121: assign l15_req_o.l15_invalidate_cacheline = '0; ✗✗✗ BROKEN HERE
 → Ariane wt_dcache.sv: NO inval/snoop input port exists (0 ports found) ✗✗✗
 → Ariane L1 D-cache never invalidates the stale line
 → Tile B reads stale data from L1 → coherency violation
```

**Evidence from RTL source:**

1. **L2 directory IS implemented and functional**: `l2_dir_wrap dir_wrap(...)` instantiated at `l2.v:424`; `dir_sharer_S4` and `mshr_inv_counter_out` used in pipeline (`l2_pipe1.v:337,698`); MSHR invalidation forward logic in `l2_pipe2.v:174`.

2. **L1.5 invalidation port EXISTS**: `l15_wrap.v:42` has `input transducer_l15_invalidate_cacheline`; `ccx_l15_transducer.v:55` outputs it; `tile.tmp.v:259,753,848` wires it.

3. **Ariane wt_l15_adapter.v:121 explicitly disables it**:
   ```systemverilog
   assign l15_req_o.l15_invalidate_cacheline = '0; // unused by Ariane as L1 has no ECC at the moment
   ```
   And cross-invalidation output:
   ```systemverilog
   logic l15_cross_invalidation;     // unused in openpiton
   ```

4. **Ariane wt_dcache.sv has NO snoop/inval port**: Module declaration (lines 8-31) contains 0 invalidation/snoop input ports. The WT D-cache physically cannot accept external cache line invalidation.

### Comparison: SPARC vs Ariane L1 coherence

| Feature | SPARC (OpenSPARC T1) | Ariane (CVA6) |
|---------|---------------------|---------------|
| L1 D-cache type | Write-back, with ECC | Write-through, no ECC |
| L1 external invalidation (snoop) | **Implemented** (hw supports cross-invalidation) | **NOT implemented** (wt_dcache.sv has no inval port) |
| L1→L1.5 cross-invalidation output | **Connected** | **Disconnected** (`'0`, "unused in openpiton") |
| Multi-tile coherence tested? | YES (`tile1_mini` regression) | NO (only tile1) |

### Why the MMIO-read barrier works

The UART MMIO read at `0xfff0c2c005` is an **uncached** load:
- Bypasses the L1 D-cache entirely (uncached = no cache line allocated)
- Goes through L1.5 → NoC → chipset → UART → NoC → L1.5 round-trip
- Forces all prior NoC transactions (including L2 directory updates) to complete before the read returns
- Acts as a **global ordering barrier** across all tiles

This is NOT a replacement for proper cache coherence — it's a **coarse-grained serialization point** that prevents stale L1 reads by forcing uncached access at trap entry. It works because:
- Every SBI ecall/timer IRQ goes through the trap handler
- The uncached MMIO read flushes the NoC transaction pipeline
- Subsequent loads after the barrier use write-through semantics (WT D-cache → every store goes to L2 → directory is updated)
- But **stale L1 D-cache reads between barriers** can still occur (the barrier doesn't invalidate L1 lines)

### Performance impact at scale

| Config | Barriers/sec | MMIO port load | Per-core overhead | Verdict |
|--------|-------------|----------------|-----------------|---------|
| 64 cores | ~7,000 | 0.7% | <0.1% | ✅ Negligible |
| 1024 cores | ~1,200,000 | 120% (overloaded) | ~1.4% | ❌ Port bottleneck |

### The correct fix: implement L1 snoop in Ariane wt_dcache

Modify `wt_dcache.sv` + `wt_l15_adapter.sv` to:
1. Add an external invalidation input port to `wt_dcache.sv` (snoop interface)
2. Connect `l15_req_o.l15_invalidate_cacheline` to the snoop logic (instead of `'0'`)
3. When invalidation is received, flush the matching way in the WT D-cache tag array
4. Connect `l15_cross_invalidation` output so the L2 directory knows when the L1 invalidates a line

This is a medium-effort RTL change (~1-2 weeks) that would make `fence rw,rw` work correctly, eliminating the need for the MMIO barrier workaround entirely. It is the prerequisite for the P4 (1024-core) target.

## 2026-06-22 -- ROOT CAUSE of PMP gate: memrange splitting into power-of-2 chunks exceeds 16 PMP entries; fix = coarser align (dbg11)

- After dbg8 reached the banner, the next gate was `init_coldboot: hart isolation configure failed (error -1)` / `error: insufficient PMP entries` from `sbi_hart_oldpmp_configure`.
- **dbg9** (force old PMP — `sbi_hart_pmp_init` always registers `pmp_protection` (old, rating 100), never `epmp_protection` (SMEPMP, rating 200); `epmp_protection` marked `__attribute__((unused))`). Result: **STILL fails "insufficient PMP entries"** → the root domain genuinely has > 16 memregions, not just SMEPMP's 2-entries-per-region.
- **Statically traced all root-domain memregion sources** (`sbi_domain_init` fw region + each `sbi_domain_root_add_memrange` caller). Found the real mechanism: `sbi_domain_root_add_memrange(addr, size, align, …)` **splits each region into power-of-2 chunks of size `align`** (the loop: `rsize = align` when `pos` is aligned). With the devices' `align=0x1000`, the MMIO regions fragment into many tiny PMP entries:
  | region | addr / size | align | # PMP chunks |
  |--------|-------------|-------|--------------|
  | fw (sbi_domain_init) | 0x80000000 | — | 2 |
  | **mtimer (CLINT)** | 0xfff1024000 / 0x8000 | `MTIMER_REGION_ALIGN=0x1000` | **8** |
  | **mswi (CLINT)** | 0xfff1020000 / 0x4000 | `ACLINT_MSWI_ALIGN=0x1000` | **4** |
  | plic | 0xfff1100000 / 0x240000 | 1 MB | 3 |
  | uart8250 | 0xfff0c2c000 / 0x1000 | 0x1000 | 1 |
  | **total** | | | **≈18 > 16** → `is_valid_pmp_idx` fails at pmp_idx 16 |
  (Ariane implements 16 PMP entries; `sbi_hart_pmp_count`=16.) So it is NOT the number of devices — it is the per-device memrange **fragmentation at 4 KiB align**.
- **dbg11 fix:** raise the memrange `align` so each device splits into fewer chunks:
  - `MTIMER_REGION_ALIGN`: `0x1000` → `0x4000` (mtimer: 8 → 2 chunks; the define is memrange-only, not used in the mtimer sanity check which uses `ACLINT_MTIMER_ALIGN=0x8`).
  - `aclint_mswi.c` `sbi_domain_root_add_memrange` call: `ACLINT_MSWI_ALIGN` → `0x4000` (mswi: 4 → 1 chunk; only the memrange call changed, not the sanity-check define).
  - New total ≈ fw(2)+mtimer(2)+mswi(1)+plic(3)+uart(1) = **9 < 16**. dbg11 also keeps the per-region dump print in `sbi_hart_oldpmp_configure` to confirm the chunk count at runtime.
- Lesson (concepts): OpenSBI's `sbi_domain_root_add_memrange` fragments any non-power-of-2 / poorly-aligned MMIO window into `align`-sized PMP memregions. With a 4 KiB `align` and several KB-to-MB-sized device windows, a small handful of devices can exhaust a 16-entry PMP. When bringing up a platform with multiple MMIO devices, set each device's memrange `align` to the largest power-of-2 that its window is aligned to (so it becomes 1–2 chunks), keeping the total under the hart's PMP count.

## 2026-06-22 -- DEFINITIVE ROOT CAUSE (disasm): `struct plic_data plic_data = plic` copies 432 B, overflows the 224-B stack frame into saved s0/s1/ra

- Statically proved via the compiled disasm of `openpiton_early_init` (no simulator needed). `struct plic_data plic_data = plic;` compiles to a 432-byte struct-copy loop: source `plic` (0x80041640) → dest `mswi` (0x800417f0), stride 48 B, 9 iters = 432 B. GCC uses the **source object's actual size** for a flex-array (`s16 context_map[][2]`) struct assignment — and the static `plic` carries the 64-entry `context_map` initializer I added, so GCC copies the full object (fixed members + 64 context_map entries + padding), **not** `sizeof(struct plic_data)`(=32).
- The local `plic_data` sits at `sp+16` in a **224-byte** frame (`addi sp,sp,-224`); saved regs are `s2@192, s1@200, s0@208, ra@216`. The 432-B copy writes `sp+16 … sp+448`, blowing **224 B past the frame** and overwriting the saved `s2/s1/s0/ra` with `plic` data — exactly the `0x0004…0x000f` pattern (`context_map[2..7] = {4,5},{6,7},…,{14,15}`). On return, `ret` loads the corrupted `ra=0x000f000e000d000c` → instruction-access-fault (`mcause=1`). This is the coldboot trap seen in dbg6/dbg7, **hartid-independent** (same pattern for coldboot hart4 and hart1) because the copy is fixed-size.
- Why it only bites at 64 cores: the original `OPENPITON_DEFAULT_HART_COUNT=3` made `plic.context_map` 3 entries (≈12 B); the copy was small enough to stay within the frame. Expanding `context_map` to 64 entries (the 64-hart fix) grew the copy to 432 B → overflow. So this is a **second-order bug unmasked by the 64-hart fix**.
- **Fix = dbg8**: remove the stack-local `struct plic_data plic_data` entirely; `fdt_parse_plic(fdt, &plic, …)` parses directly into the static `plic`. - Lesson (concepts): a stack-local `struct X x = static_x;` where `X` has a **flexible array member** is a latent stack-overflow trap — GCC's struct assignment copies the *source object's* real size (incl. its flex-array initializer), not `sizeof(X)`.
