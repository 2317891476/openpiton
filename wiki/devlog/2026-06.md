## 2026-06-01 -- Build 56 dual-pin dual-protocol SD probe plan

- Build 55 showed that registering `sd_clk_out` at the IOB boundary is not sufficient: the native SD initializer still waits in `ST_ACMD41_CMD55_WAIT_INT` for a CMD55 response start bit.
- The remaining high-risk ambiguity is now physical/protocol alignment, not UART, DDR, debug hub, CPU fetch, or single SD-clock output style. The reference project proves a SPI-mode SD path on `CV57/DB57/DC56/DC55/CY56/CY55`, while `p3_io.md` lists a different PHC3 native SD mapping.
- Build 56 will be a standalone minimal design, not a full OpenPiton build. It will use the proven Versal debug-hub/ILA path and a small RTL SD command engine to test both pin maps and both protocol assumptions from one bitstream.
- VIO controls will select `pin_sel` (`reference` or `p3_io.md PHC3`) and `proto_sel` (`SPI` or native SD CMD). ILA captures will record CMD/DAT input/output/enable levels, response detection, timeout, state, and pass/fail code.
- Decision table: reference+SPI response means the next OpenPiton direction should use a SPI SD controller path; p3_io+native response means the next full build should only fix XDC pin mapping; reference+native response means the fault is inside the OpenPiton native controller integration; no response on all combinations means the SD power/reset/slot/card path must be verified externally.

## 2026-06-01 -- Build 54 Review: Analyzing CMD55 Timeout & SPI Wire-Crossing Hypothesis

- Evaluated Build 54's decoded ILA trace: the serial host stays stuck in `READ_WAIT` (0x08) and `ST_ACMD41_CMD55_WAIT_INT` (0x34) waiting for the response start bit. This rules out simple idle-line pull-up issues.
- Analyzed the mismatch between `constraints.xdc` and `p3_io.md`. However, UART works perfectly on `CW58/CW59` (B3/B2) instead of the manual's `CM59/CN59` (C8/C9), proving that the board routing differs from the manual's PHC3 section.
- Formulated the **SPI Wire-Crossing Hypothesis**: the reference project (`shell.xdc`) routed SD in SPI mode, where `DB57` served as SPI_CS (connected to Card DAT3) and `CY55` served as SPI_DI (connected to Card CMD). OpenPiton's native SD controller outputs `sd_cmd` on `DB57` and `sd_dat[3]` on `CY55`, physically misrouting CMD to DAT3 and DAT3 to CMD.
- Plan: Build 55 proceeds as scheduled to test the IOB SD clock register (`huaprop3_build55_sd_clk_iob_reg` in `D:/p3b55`).
- Plan: A new dedicated **Build 56** will be set up to run physical pin experiments:
  - Swap `sd_cmd` (CY55) and `sd_dat[3]` (DB57) under the reference pinout to test the SPI wire-crossing hypothesis.
  - Generate a secondary build mapped to `p3_io.md`'s PHC3 native SD pins to test the manual alignment.

## 2026-06-01 -- P3 Build 51 hardware result: SD card-detect holds native SD reset

- Build 51 completed from `D:/p3b51` and published `huaprop3_build51_sd_init_debug/debug_build/p3_top_build51_sd_init_debug.pdi` and `.ltx`. Top synthesis, placement, route, and `write_device_image` completed with 0 errors; route status had 0 failed nets and the post-route estimate was positive (`WNS=9.131 ns`, `WHS=0.006 ns`).
- Programming through `hw_server 100.93.77.36:3121` and XVC `202.197.4.99:2540` succeeded with `DONE bit: HIGH`. The debug hub refreshed through `PMC_AXI_NOC0` at `0x3ffc0000000`, and all four BD-owned ILAs exported CSV.
- Decode reported `top_status=0xff00`, `core_seen=0x7fff`, SD-init seen bits `0x00cb`, and DDR seen bits `0x8001`. The SD-init live bus was `0x0000280001f01066`.
- The decisive SD-init bits are `sd_cd=1`, aggregated SD reset `rst=1`, `init_done=0`, `wb_stb=1`, `wb_we=1`, `wb_ack=0`, `sd_clk_toggle=0`, and no CMD/DAT output-enable activity. Because `piton_sd_top` defines its internal reset as `sys_rst | sd_cd`, the observed high card-detect input holds the SD controller and init FSM in reset.
- This explains the Build 49/50 symptom `buf_sd_noc2_valid=1` with `sd_buf_noc2_ready=0`: the SD request path cannot accept CPU requests until `init_done` rises, and `init_done` cannot rise while the SD block is reset by card-detect. The next build should mask `sd_cd` out of the internal reset while still probing the raw card-detect input.
