## 2026-07-09 -- Static deep-dive: L1.5 WMT write-guard removed "for timing" is a concrete suspect for the intermittent stale-L1 hang

Since sim exhausts the RTL-functional coherence hypotheses (all coh_* PASS) but
the board hangs intermittently under load, I traced the ONE piece of L1.5
coherence state that (a) gates whether an invalidation reaches the L1 D-cache
at all, and (b) has an explicit "timing fix" that dropped a hazard guard: the
**Way-Map Table (WMT)**.

### Why the WMT is the linchpin of L1 invalidation

The L1.5 does not track which L1-D way holds a line directly; it keeps a WMT
(`rf_l15_wmt.v.pyv`, one entry per L1D set) mapping L1.5 line -> L1D way. When a
remote store forces an invalidation, the pipeline forwards it to the core ONLY
if the WMT lookup matches (`l15_pipeline.v.pyv:3904`):
```
`L15_CPX_GEN_INVALIDATION_IF_TAGCHECK_MES_AND_WAYMAP_VALID:
    cpx_req_val_s3    = tagcheck_state_mes_s3 && wmt_compare_match_s3;  // WMT-gated
    cpx_inval_way_s3  = wmt_compare_match_way_s3;                       // way from WMT
```
So a stale/incorrect WMT read => the invalidation is silently dropped or sent to
the wrong way => the L1 keeps a stale line => a spinning reader reads the old
value forever. That is exactly the stop_machine / XSBench symptom.

### The WMT RAM has a 2-cycle write latency and NO write-to-read bypass

`rf_l15_wmt.v.pyv`: read is `regfile[read_index]` registered (issue s2, data
s3). Write is registered TWICE: `write_valid`->`write_valid_f` (1 cyc), then the
actual `regfile[write_index_f] <= ...` on the NEXT cycle. So a WMT write decided
in s3 lands in the array **2 cycles after s3**, and the read port does not
forward the pending `write_data_f`.

### The removed guard (the concrete suspect)

`l15_pipeline.v.pyv:3776-3778`:
```
// trin: timing fix: removing guard for wmt writes; should still be correct
// l15_wmt_write_val_s3 = wmt_write_val_s3 && !stall_s3 && val_s3;
l15_wmt_write_val_s3 = wmt_write_val_s3 && val_s3;   // <-- !stall_s3 dropped
```
The WMT write now fires even while s3 is stalled. `stall_s3 = stall_for_cpx_s3
|| stall_for_noc3_s3` -- i.e. it stalls whenever the CPX (response-to-core) or
NoC3 (writeback-to-L2) channel is congested. **Under 64-core load those channels
are frequently congested, so s3 stalls are common** -- load-dependent, matching
the board behaviour and the sim's inability to reproduce (the sim's
zero/fixed-latency `fake_mem_ctrl` almost never congests CPX/NoC3).

### The hazard window (hypothesis, not yet proven)

The index-conflict guard that protects back-to-back same-set accesses only
covers the s2/s3 slots:
```
stall_index_bypass_match_s1 = (val_s2 && idx_s1==idx_s2) || (val_s3 && idx_s1==idx_s3);
```
But the WMT write completes 2 cycles AFTER s3. When s3 is stalled for multiple
cycles with the write-guard removed, the timing relationship between "when the
WMT write actually lands" and "when a following same-index request's s2 read
samples the array" shifts by the stall length. The guard reasons about pipeline
slots (s2/s3), not about the RAM's internal 2-cycle write pipe, so a stalled-s3
WMT write racing a trailing WMT read of the same index is not obviously covered.
If that read samples the array in the 1-cycle gap before the delayed write
lands, it gets stale way-map data -> wrong/dropped invalidation.

This is a **specific, code-anchored hypothesis**, NOT yet proven. It is exactly
the class the fixed-latency sim can't hit and STA can't see (functional protocol
race, not setup/hold), and it is load-gated (needs CPX/NoC3 congestion to stall
s3), which fits "passes light diags, hangs under heavy 64-core traffic".

### Next steps to prove/disprove
1. Build a focused sim assertion: in `cmp_l15_messages_mon`, flag any cycle
   where `l15_wmt_write_val_s3` is high while `stall_s3` is high AND a WMT read
   to the same index is in s2 within the next 2 cycles. Run the existing 8x8
   model under coh_stopmachine + an added CPX/NoC3 backpressure injector so s3
   actually stalls (the missing ingredient the fake mem never provides).
2. If confirmed, the fix is to restore the guard (or add a WMT write-to-read
   bypass / extend the index-conflict stall to cover the RAM's 2-cycle write
   pipe). Cheap to try: re-add `&& !stall_s3` and re-run the board XSBench/boot.
3. Board-side cross-check: the earlier proposal (a kernel module hammering
   stop_machine, dumping the stuck hart's PC/satp) still distinguishes "stale L1
   data" (this hypothesis) from an MMU/TLB or IPI-delivery cause.

## 2026-07-08 -- coh_stopmachine PASSES too: sim exhausts the shared-memory/coherence hypotheses; failure is NOT in a layer the sim models

`coh_stopmachine.c` (the diag purpose-built to mirror `multi_cpu_stop`: leader
plain-stores a shared `state` through 8 phases, 63 followers tight-spin reading
it) ran on the instrumented 8x8 model: **Hit Good trap at main_time 44M, zero
COH_IPI64_MONFAIL, zero stuck_hart** -- all 8 rounds of cross-hart shared-state
visibility converged cleanly at 64 cores (43 min wall).

### The full simulation ledger now

| diag | pattern under test | result |
|------|--------------------|--------|
| coh_2core | 2-core L1 invalidate (store->load) | PASS |
| coh_64core | 64-core broadcast invalidate | PASS |
| coh_ipi64 x4 | MSIP send + poll pending bit + slots[] | PASS x4 |
| **coh_stopmachine** | **multi_cpu_stop tight shared-state spin** | **PASS** |

I deliberately built the last diag to be the closest possible match to the
board's failing pattern (concurrent tight shared-writer visibility, the exact
thing hypothesis #1 blamed). It still passes. Combined with the instrumented
monitor never tripping, this is a decisive **negative result**: in a
cycle-accurate 64-tile RTL simulation, the L1/L2/NoC coherence + shared-memory
ordering path is functionally correct even for the multi_cpu_stop access
pattern. Hypothesis #1 ("cross-hart shared-memory ordering race in the RTL") is
now itself largely falsified at the RTL-functional level.

### What this redirects to: the failure lives in a layer the sim does NOT model

The sim is RTL-cycle-accurate but omits exactly the things that differ between
"diag passes" and "board hangs":

1. **Real DDR3 / MIG + asynchronous clock domains.** Sim uses a behavioral,
   near-deterministic memory model. The board has real DDR3 refresh, MIG
   calibration latency, and NoC<->chipset<->DDR clock-domain crossings
   (`noc_mig_bridge.v`, async FIFOs). A coherence/ordering hazard that only
   manifests under real memory latency or a marginal CDC would pass in sim and
   hang on the board.
2. **MMU / TLB / S-mode.** The board runs full Linux: `multi_cpu_stop` executes
   with the MMU on, page-table walks, and TLB state; stop_machine is often used
   precisely for TLB shootdown-adjacent work. Our diags are bare-metal M-mode,
   physical addresses, no MMU/TLB. A TLB or page-table-walk coherence issue is
   invisible to these diags.
3. **True concurrency of timer + IPI + workload.** The board has 250 Hz timer
   IRQs on all 64 harts plus IPIs plus real memory traffic, all at once. The
   diags exercise one pattern with no concurrent timer/IRQ.

### Revised conclusion + next step

The bug is very unlikely to be a pure RTL coherence-logic defect (4 diags + an
instrumented protocol monitor say the logic is correct). The strongest
remaining suspects are the ones the sim cannot see:
- **(a) real-hardware timing / CDC / DDR-latency-dependent ordering hazard**, or
- **(b) an MMU/TLB-level coherence or shootdown issue under Linux**, or
- **(c) the dbg21 MMIO-read barrier being insufficient at 64 cores** (it papers
  over ordering only on non-IRQ trap entry; heavy concurrent compute + timer
  IRQs have windows it doesn't cover -- consistent with XSBench hanging in
  heavy-compute and boot hanging at the stop_machine after clocksource init).

Because sim has been exhausted for this class, the decisive next step is
**board-side, not more sim**:
- Add a tiny **Linux kernel module** that runs a `multi_cpu_stop`-style
  all-hart tight shared-state spin (or just calls `stop_machine()` in a loop)
  and, on timeout, dumps **which hart** failed to observe the shared update and
  its `satp`/`sstatus`/PC -- distinguishing (b) MMU/TLB from (a) plain memory.
- OR the ILA on CLINT `msip_q`/`ipi_o` + the NoC-to-DDR bridge handshake, to
  catch (a) a timing/CDC stall that sim's behavioral memory can't reproduce.
- Also worth a cheap test: re-enable the dbg22 all-traps barrier BUT only after
  the IRQ ack (fixing the dbg22 livelock) -- if that makes the hang go away,
  it's (c) barrier-coverage.

Net: the "coherence race" has been chased into a corner where sim says the RTL
logic is correct; the remaining truth is at the hardware-timing or MMU layer,
which only board instrumentation can see.

## 2026-07-07 -- Re-analysis: "MSIP delivery to 58 harts broken" is FALSIFIED; real suspect narrows to a concurrent-IPI ordering/coherence race

Went back over the wiki logs + static evidence instead of pushing the blocked
OpenSBI probe. The prior "stop_machine IPI deadlock => 58/64 harts never get
their MSIP" root-cause statement is **over-read and internally inconsistent**.
Correcting it.

### Falsification 1: SMP bringup already proves MSIP delivery works for all 64 harts

Static: OpenSBI `sbi_hsm.c:168-186` -- a secondary hart parks in
`sbi_hsm_hart_wait` with `csr_set(CSR_MIE, MIP_MSIP|MIP_MEIP)` then `wfi()`.
It is woken **only** by an MSIP IPI (`hart_start` -> `sbi_ipi_raw_send`). So
every secondary that comes online was woken from `wfi()` by an MSIP.

Board log (dbg27, `b0369yu8y.output`): `smp: Brought up 1 node, 64 CPUs`,
`online_cpus=64`. **All 64 harts were successfully woken by MSIP.** Therefore
the CLINT MSIP -> per-hart interrupt-line delivery path is **functional for all
64 harts** -- a permanently broken wire/route to 58 harts is impossible, or
those harts would never have come online. The earlier "58 harts never respond
to the IPI" is falsified.

### Falsification 2: soft-lockup absence != "hart didn't get the IPI"

The 6 CPUs that report soft lockup are `{0,1,3,4,11,12}`. I previously read the
other 58 as "did not respond to the stop IPI". That is a misread of the
soft-lockup mechanism:

- soft lockup is a **per-CPU** watchdog: a CPU prints **only if its own timer
  IRQ is still alive** AND it has been stuck >20 s in a non-scheduling loop.
- So the 6 reporters = harts that (a) got the stop IPI, (b) entered
  `multi_cpu_stop`, and (c) still have a live timer IRQ to run the watchdog.
- The silent 58 are **not** necessarily "IPI lost". They split into: harts
  parked idle (nothing to report), harts stuck with a **dead** timer IRQ
  (can't print), or harts stuck elsewhere. Absence of a soft-lockup line
  carries almost no information about IPI receipt.

So the headline number "6/64 responded" does **not** mean "58 IPIs lost".

### What actually differs: bringup (works) vs stop_machine (hangs)

Both use the same CLINT MSIP hardware, so the bug is not the wire. The
differences that matter:

1. **Concurrency/contention.** Bringup is sequential/batched -- harts woken
   with low simultaneous NoC load. stop_machine fires IPIs to all 63 harts
   near-simultaneously **and** each acks back, a burst of concurrent MSIP MMIO
   writes + returns through the NoC/chipset CLINT bridge under contention.
2. **Privilege/MMU state.** At bringup the target sits in M-mode `wfi`. At
   stop_machine the target runs S-mode Linux with the MMU on; the IPI must be
   taken as M-mode MSIP, reflected to S-mode SSIP (`sbi_ipi_process` ->
   `csr_set(MIP, MIP_SSIP)`), and delivered through Linux's irq path. More
   stages, more shared state.
3. **Shared-memory sync, not just the interrupt.** `multi_cpu_stop` is a
   spin-loop state machine over a **shared `multi_stop_data` struct** in DRAM:
   every hart must SEE the state advance (MULTI_STOP_PREPARE -> DISABLE_IRQ ->
   RUN -> EXIT) written by the leader. This is exactly the cross-hart
   shared-writer visibility that the silent MMIO-read coherency barrier (dbg21)
   was patching. If a hart's view of `msdata->state` is stale, it spins forever
   even though its IPI arrived fine.

### The strongest under-weighted lead: the sim DID reproduce an L1.5 anomaly on the IPI/sync path

`coh_ipi64.c` on the 8x8 Verilator model produced an intermittent
`cmp_l15_messages_mon` failure -- an L1.5 DTAG/protocol anomaly around a TILE0
store at `0x8020e9c`, on the IPI/sync path. It was later demoted to a "stale
lead" only because a low-overhead *progress-only* sweep didn't re-trip the
monitor in 3 runs -- that is weak evidence of absence (the monitor prints were
suppressed for speed, and the fail is intermittent). Crucially, `coh_64core`
(AMO/store broadcast) did **not** trip it, but `coh_ipi64` (MSIP + tight
cross-hart sync) did -- the anomaly is specific to the interrupt/sync pattern,
which is exactly `multi_cpu_stop`.

### Revised root-cause hypothesis (ranked)

1. **Cross-hart shared-memory ordering/visibility race in `multi_cpu_stop`'s
   `msdata->state`** (a coherence/ordering problem on the sync variable, NOT a
   lost interrupt). Fits: bringup works (little shared spinning) but
   stop_machine hangs (tight shared spin); dbg21 needed an MMIO-read barrier
   for exactly this class; the `coh_ipi64` L1.5 anomaly is on this path;
   intermittent + timing-dependent; XSBench unionized-grid (heavy shared
   sync) hangs the same way.
2. **Concurrent-IPI ordering bug** in the CLINT bridge / `sbi_ipi` fast-path
   under a simultaneous 63-way storm (e.g. the `__atomic_fetch_or(ipi_type)`
   "only send if was 0" optimization dropping a needed re-send when an ack and
   a new send race). Lost/merged IPI, but only under the storm.
3. **Timer IRQ death on the stuck harts** (the silent 58 include harts whose
   timer stopped), making it look like more harts are stuck than the 6 that can
   still print.

### Why this matters / next step

The blocked OpenSBI MSIP write+readback probe was testing hypothesis "MSIP
doesn't reach CLINT" -- which Falsification 1 already makes unlikely. Higher
value now:

- **Re-run `coh_ipi64` with the messages-monitor fail branch actually
  instrumented** (compact context print on the real `MONITOR_PATH.fail`), loop
  until it trips, and capture a narrow VCD of the TILE0 L1.5 `0x8020e9c`
  DTAG/MESI transition + the CLINT MSIP return flit. This directly tests
  hypothesis #1/#2 in sim, no board churn, no OpenSBI rebuild.
- Alternatively, a board-side software test that is decisive without ILA:
  a tiny kernel module / bare-metal loop that hammers `multi_cpu_stop`-style
  all-to-all IPI + shared-flag spin and counts which harts fail to observe the
  flag (distinguishes "IPI lost" from "shared read stale").
- ILA on CLINT `msip_q[63:0]`/`ipi_o[63:0]` remains the hardware-truth
  fallback, but it tests the *least* likely hypothesis first, so it is not the
  cheapest next step.

Bottom line: the failure is most likely a **cross-hart shared-memory
ordering/coherence race on `multi_cpu_stop`'s sync state under concurrency**,
not a broken per-hart MSIP wire. This also re-opens the question of whether the
dbg21 MMIO-read barrier is truly sufficient at 64 cores or just shifts the race
window.

## 2026-07-06 -- SBI-IPI->CLINT MSIP link full static audit: all code correct, bug is runtime

Per the user's link diagram and probability ranking, statically audited every
stage of Linux stop_machine -> SBI ecall -> OpenSBI -> CLINT MSIP -> interrupt
distribution -> tile. Conclusion: **the static code is correct at every stage;
there is no code bug**. The 58/64 non-respond is a runtime hardware behavior
(MSIP written but interrupt not delivered).

Per-stage audit (all PASS):
- DTB `cpu@N reg=<N>` (`p3_generate_opensbi_dts.py:11`) -- hartid 0..63 contiguous.
- mhartid==flat_id==cpu index -- proven by successful 64-CPU bringup.
- Linux `__sbi_send_ipi_v02` (`sbi.c:238`): `sbi_ecall(IPI, SEND_IPI, hmask=1, hbase=cpuid_to_hartid_map(cpu))` -- per-CPU ecall, hmask=1 correct.
- OpenSBI `sbi_ipi_send_many` (`sbi_ipi.c:118-172`): `weight==count` validation passes (else `SBI_EINVAL` + pr_err).
- OpenSBI `mswi_ipi_send` (`aclint_mswi.c:44`): `writel_relaxed(1, msip[hartid-first_hartid])` -- offset correct, matches `clint.sv` decode.
- OpenSBI `sbi_ipi_process` (`sbi_ipi.c:259-271`): `raw_clear -> xchg(ipi_type,0) -> loop` -- standard read-clear-process, xchg cannot lose a bit. `raw_send`/`raw_clear` wmb pairing correct.
- chip-level `ipi_i[63:0]` distribution (`chip.tmp.v`): all 64 tiles wired to `ipi_i[flat_id]` (count=64, identical to `timer_irq_i`).

Discriminating evidence:
- UART log has **zero** SBI IPI errors (grep `__sbi_send_ipi_v02`/`hbase failed` empty) -> all 64 ecalls succeed, OpenSBI really wrote 64 MSIPs (weight checks all pass).
- Yet only 6/64 harts `{0,1,3,4,11,12}` entered `multi_cpu_stop` (reported migration soft lockup); 58 did not respond.

Statically exonerated: #6 timer (soft lockup proves timer alive); #2 cpuid<->hartid mapping (DTB reg contiguous + bringup OK + no ecall errors); #3 OpenSBI hmask/hartid handling (`sbi_ipi_send_many` + mswi offset correct); code-level #1 (MSIP offset decode correct).

Converges to runtime suspects (invisible to static reading):
- MSIP MMIO write actually failed to set `msip_q[h]` in CLINT despite OpenSBI getting the B response (#1 runtime, needs ILA on `msip_q`).
- `ipi_o[h]` -> tile h interrupt line / 2-flop synchronizer intermittently fails for 58 harts.
- `ipi_type` shared cache-line coherence (#5, hart0 atomic write to remote scratch not visible to remote).
- 58 harts in idle, idle-state MSIP handling issue.

The 6/64 structural split `{0,1,3,4,11,12}` cannot be explained statically; needs runtime to see if the responder set is fixed across boots (structural) or random (NoC loss).

Next: build a runtime probe. dbg28 = `nowatchdog` to skip the boot-time stop_machine -> reach shell -> IPI ack-count probe (each CPU increments a shared counter on IPI; tally which CPUs respond); if shell unreachable, escalate to ILA on CLINT `msip_q[63:0]`/`ipi_o[63:0]` for deterministic hardware truth.

## 2026-07-06 -- dbg27 ROOT CAUSE: stop_machine IPI deadlock (timer exonerated; __do_softirq EPC mystery solved)

dbg27 (bootargs add watchdog/panic_on_warn; zero-synth, zero-sim) captured the
decisive root-cause evidence: the 64-core boot hangs at ~32s right after
`clocksource_done_booting`, and it is a **stop_machine IPI deadlock**, NOT timer
data corruption. The timer is fully exonerated.

Decisive stack (from the soft-lockup dump):
```
Stopper: multi_cpu_stop+0x0/0x14a <- stop_machine_cpuslocked+0xcc/0xfc
epc : __do_softirq+0x9e/0x25a
ra  : __irq_exit_rcu+0x8e/0xb4
```

Two iron-clad facts:
1. **`Stopper: multi_cpu_stop <- stop_machine_cpuslocked`** -- stuck in
   **stop_machine**. The migration kthread is busy-waiting in `multi_cpu_stop`
   for all harts to reach the stopmachine state.
2. **`epc: __do_softirq+0x9e`** -- **this is exactly the EPC that was misread
   for weeks as "the timer crash site"**. Real context: while the migration
   thread busy-waits in `multi_cpu_stop`, the timer interrupt fires normally
   (timer is innocent), and on IRQ exit the path is `__irq_exit_rcu` ->
   `__do_softirq`, so EPC lands at `__do_softirq+0x9e` -- the softirq entry
   boundary (the `csrsi sstatus,2` re-enable-interrupt spot identified in the
   2026-07-04 static check). It is an IRQ return address, NOT a fault site.
   The "timer data structure corruption" hypothesis is definitively dead.

CPUs that responded to stop_machine and are busy-waiting in `multi_cpu_stop`
(reported migration soft lockup):
- CPU#0 (migration/0, 218s) -- boot CPU, the stop_machine initiator, also waiting
- CPU#3 (34s), CPU#4 (50s), CPU#11 (154s), CPU#12 (170s)
(list still growing; per-CPU independent detection at different thresholds)

All of these have **live timer interrupts** (soft-lockup detection runs off the
timer-driven watchdog hrtimer), so the timer is completely innocent. They are
stuck in `multi_cpu_stop` because **some hart(s) never responded to the
stop_machine IPI**.

Root-cause direction: **stop_machine IPI delivery intermittently fails**.
stop_machine sends IPIs via SBI ecall -> OpenSBI -> CLINT MSIP MMIO write
(NoC -> chipset CLINT) to all 64 harts. Some hart never sees its MSIP -> its
migration thread never runs `multi_cpu_stop` -> every hart that did respond
busy-waits forever in `multi_cpu_stop` with no request-timeout (the 2026-07-04
no-timeout finding is exactly why this is a silent permanent hang). This narrows
the failure class from "memory/IO response loss" to specifically **IPI (CLINT
MSIP) delivery**, consistent with the 2026-07-04 convergence.

The demoted `coh_ipi64.c` 3-pass sweep was correctly demoted for an unloaded
sequential MSIP test; boot-time concurrent + real-SBI-ecall MSIP delivery is a
different regime. A new concurrent IPI stress probe is needed to reproduce.

bootargs lesson: `softlockup_panic=1` / `rcu_cpu_stall_timeout=10` /
`nmi_watchdog=1` were rejected as "unknown kernel command line parameters" (the
6.6 RISC-V kernel does not register them as `__setup` bootargs). Correct form is
`rcupdate.rcu_cpu_stall_timeout=10`. But `watchdog_thresh=10` + `panic_on_warn=1`
+ `CONFIG_SOFTLOCKUP_DETECTOR=y` (default on) were enough to fire this detection
(soft-lockup BUG + full stack). Next dbg28 should use `rcupdate.rcu_cpu_stall_timeout=10`
to also get the RCU stall (21s default), which names the non-responding hart.

Next steps:
1. Wait for / force an RCU stall to dump all CPU stacks -> identify the exact
   non-responding hart.
2. Write a concurrent IPI stress diag (64-hart simultaneous stop_machine-style
   MSIP storm) to reproduce MSIP loss.

## 2026-07-04 -- Static check refutes kernel timer data-corruption hypothesis

Static review of the kernel-side timer/softirq path refutes the working
hypothesis that 64-core instability comes from corrupted Linux timer data
structures (hrtimer / `timer_list` linked lists).

- **Kernel is 6.6.0**, not 5.1.0-rc7. (5.1.0-rc7 is the Build 66 BBL baseline;
  the 64-core OpenSBI/Linux path uses 6.6.) Config: `NR_CPUS=64`, `HZ=250`,
  `NO_HZ_IDLE=y`, `HIGH_RES_TIMERS=y`, `PREEMPT_NONE=y`, `DEBUG_INFO_NONE=y`,
  and **`DEBUG_LIST/DEBUG_SG/DEBUG_PLIST=y`** (linked-list integrity self-checks
  enabled).
- **Crash EPC reinterpretation.** `__do_softirq` is at `0xffffffff807fa0b6`;
  crash EPC `0xffffffff807fa154` = `__do_softirq+0x9e`. Disassembly shows the
  instruction there is `sext.w a5,s11`, immediately preceded by
  `csrsi sstatus,2` (re-enable S-mode interrupts). `__do_softirq` explicitly
  `local_irq_enable()` before draining the softirq backlog; a pending timer
  interrupt is sampled at that boundary with EPC pointing to the next
  (non-memory, non-faulting) instruction. So this EPC is the **normal S-mode
  timer-interrupt entry boundary**, not a fault inside list traversal.
  `cause=0x8000000000000005` is "S-mode timer interrupt" (bit 63 set),
  consistent with this. The earlier "traversing a corrupted list -> crash"
  reading is wrong; `sext.w` cannot fault.
- **`DEBUG_LIST/SG/PLIST=y`** means software list corruption would WARN/BUG
  with a stack trace before any silent hang. No such warning appears in any
  captured log -> no evidence of software-corrupted timer lists.
- **`__hrtimer_run_queues`** (`kernel/time/hrtimer.c`) and the RISC-V timer
  driver (`drivers/clocksource/timer-riscv.c`) are standard upstream code with
  no 64-core-specific anomaly visible statically. No SSTC on this CVA6, so the
  kernel programs the timer via `sbi_set_timer()` ecall -> OpenSBI -> CLINT
  mtimer (M-mode side already verified correct in the 2026-07 deep-dive).
- **Decisive argument against a software timer bug:** the failure is
  **intermittent with the SAME PDI/SD image** -- sometimes boots fully to a
  64-core shell, sometimes stalls at `[0.000000]`. A deterministic kernel
  data-structure corruption would reproduce every boot. Intermittency =>
  timing/race in a path exercised by SMP bring-up and heavy parallel compute,
  not a software bug in timer data.
- **Evidence converges on the interrupt/timer-IPI delivery round-trip:** CPU
  MMIO write (CLINT MSIP for IPI, CLINT mtimer for timer) -> NoC -> chipset ->
  CLINT register, with the resulting interrupt routed back to a target hart.
  Both `stop_machine` (`IPI_CPU_STOP` to all 64 harts) and the early boot stall
  require reliable per-hart interrupt delivery. Hypothesis #3 (NoC/memory
  subsystem intermittent) is the best fit, **specifically the per-hart CLINT
  interrupt delivery path**, not random memory data corruption.
- **Next target:** statically inspect the OpenPiton chipset CLINT MSIP/mtimer
  interrupt-injection path, then add a stress probe (64-hart MSIP storm that
  mimics `stop_machine` timing under NoC load) to reproduce the intermittent
  loss. The demoted `coh_ipi64.c` used a 4M-cycle spin limit and only tested
  MSIP visibility under no load; it was not representative of the kernel's
  all-hart-simultaneous IPI under NoC contention.

## 2026-07-03 -- OpenSBI timer path deep-dive: code is CORRECT — corruption is in kernel timer DATA

### Crash disassembly analysis

The crash EPC `0xffffffff807fa154` (`__do_softirq+0x9e`) disassembles to:
```asm
ffffffff807fa154:  000d879b    sext.w  a5, s11   # sign-extend register, NOT a load
```

**Key corrections from earlier analysis:**
- `cause = 0x8000000000000005`: bit 63 SET → this is a **S-mode timer INTERRUPT**, not a Load Access Fault (which would be cause=5 without bit 63).
- `badaddr = 0xd879b`: for interrupts, sbadaddr is not updated. This value (= the instruction encoding `0x000d879b`) is **stale/garbage** — the trap frame itself may be corrupted.
- The EPC instruction (`sext.w`) cannot fault — confirming the crash state is corrupted.

### OpenSBI timer code review: all correct

Reviewed `sbi_timer.c`, `aclint_mtimer.c`, `fdt_timer_mtimer.c`:

1. **mtimecmp write**: 64-bit atomic MMIO (`writeq_relaxed`, single 64-bit write). OpenPiton CLINT has `has_64bit_mmio = true`. No split-write race.
2. **Per-hart mtimecmp**: `time_cmp[target_hart - mt->first_hartid]` with `target_hart = current_hartid()` (reads `mhartid` CSR). Correct hart indexing.
3. **Per-hart timer state**: `timer_state` in per-hart scratch, spinlock-protected. No cross-hart data race in OpenSBI's timer management.
4. **STIP forwarding**: `csr_set(CSR_MIP, MIP_STIP)` in the callback. Standard M→S timer delegation.
5. **dbg21 barrier**: runs only on non-IRQ traps (ecalls). Timer interrupts are IRQs → barrier does NOT interfere with timer path.

**Conclusion**: OpenSBI's timer code is standard, well-tested, and correct for 64 harts. No bug found.

### Where the corruption actually is

The crash is in **Linux's kernel timer softirq data structures** (hrtimer bases, timer lists, per-CPU timer data). The corruption propagates from an unknown source into the kernel's linked list / per-CPU data, and the timer interrupt handler crashes when it traverses the corrupted structures.

Possible corruption sources (not yet confirmed):
1. **Subtle coherency corner case**: coh_64core proved basic store→load visibility works, but kernel timer linked lists involve complex pointer-chasing patterns (READ_ONCE/WRITE_ONCE across cache lines, per-CPU locks, cross-CPU timer delegation). A subtle invalidation miss on a specific access pattern could corrupt list nodes.
2. **Kernel SMP bug at 64 cores**: Linux's per-CPU timer management might have a scaling issue (e.g., per-CPU data alignment, TLB pressure, or a race in the timer wheel at high core counts).
3. **NoC/memory subsystem**: intermittent data corruption during heavy 64-core memory traffic (unlikely but not ruled out).

### Next investigation targets (not yet started)
1. Test with fewer cores (2x1, 4x4) — if crash doesn't reproduce, it's 64-core-specific.
2. Add kernel-side instrumentation to the timer softirq (check list integrity before traversal).
3. Try `nohz_full` (disable timer ticks on non-boot cores) to see if the crash goes away.
4. Kernel config: `CONFIG_HZ=100` → `CONFIG_HZ=10` (reduce timer tick frequency) to see if crash frequency changes.
