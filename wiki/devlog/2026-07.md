## 2026-07-13 -- Regression NARROWED to sbi_hart.c (CSR 0x701) or sbi_trap.c via source mtime

Source-file modification times pin the no-banner regression to a tiny window.
Between the verified-banner era (dbg21 fw, 2026-06-26 15:05) and the broken fw
(dbg28b_noprobe = current source, 12b4ff22), the ONLY OpenSBI source files
changed are:
- `lib/sbi/sbi_trap.c`  (2026-06-27 16:26) — the non-IRQ UART-LSR coherency barrier (Gate 9)
- `lib/sbi/sbi_hart.c`  (2026-06-27 16:26) — CSR 0x701 L1 D-cache disable in sbi_hart_init (Gate 8)

The dbg28-era edits to `aclint_mswi.c` and `openpiton.c` (2026-07-08 20:02-20:04)
were NET-NO-OPS: a clean rebuild from the current (post-revert) source reproduces
the 7/6 dbg28b_noprobe binary byte-identical (12b4ff22), proving the probe
add+revert left no residue. So those files are NOT the regression.

Therefore the regression that breaks 2-core OpenSBI cold-boot banner is one of:
1. **CSR 0x701 L1 D-cache disable (sbi_hart.c)** — changes EVERY load/store to
   bypass L1 and hit L1.5/L2/NoC directly. Most likely 2-core-specific culprit
   because it fundamentally alters the memory-access path; a 2-tile fabric may
   not handle the L1-disabled access pattern the way an 8x8 mesh does.
2. The sbi_trap.c coherency barrier refinement — only affects trap handling,
   less likely to gate the banner (banner path has no trap unless something faults).

The dbg21 fw image (`p3_opensbi_linux_2hart_dbg21fw.img`, sha 517d9b87) predates
BOTH changes and is the direct test: if dbg21 fw prints the banner on 2-core, the
regression is confirmed to be CSR 0x701 and/or the barrier refinement, and the
fix is to gate/revert CSR 0x701 for the 2-core build (CSR 0x701 was only needed
for 64-core XSBench coherency per Gate 8).

The probe image (`p3_opensbi_linux_2hart_probefw.img`, sha b9bfcedb) localizes
which init step hangs if dbg21 also fails (would then point to a 2-core-hw issue
in CLINT/UART/console MMIO rather than a source regression).

Both images built and ready. Awaiting SD card swap (card is in the FPGA; must
move to reader to write either image, then back to FPGA to boot).

## 2026-07-13 -- Added OpenSBI cold-boot raw-UART probes to localize the no-banner hang

Static audit found all 64-core OpenSBI fixes present in 2-core source, and the
PLIC/CLINT init loops are DTB-driven (`sbi_for_each_hartindex`), so the hardcoded
`hart_count=64` is safe on 2-core (does not touch non-existent contexts). So the
no-banner hang is NOT a missing known fix and NOT a hart-count overflow.

To localize it definitively, added B69-style raw-UART probes to OpenSBI
`init_coldboot` (lib/sbi/sbi_init.c). A `p3_probe_putc(char)` helper writes
directly to AXI16550 THR (0xfff0c2c000) with LSR (0xfff0c2c005) THRE poll,
bypassing console init — same path the bootrom proved working. Probes inserted:
- `I` at sbi_init() entry (confirms OpenSBI C code starts at all)
- `[` at init_coldboot() entry
- `S H D` after scratch/heap/domain init
- `M` after hsm_init, `W` after wake_coldboot_harts
- `R` after sbi_hart_init (incl. CSR 0x701 L1 disable)
- `T` after sbi_timer_init
- `E` after sbi_platform_early_init (= generic_early_init = console/fdt init)
- `P B` after pmu/dbtr init, then sbi_boot_print_banner (the missing banner)

Reading the probe trace pinpoints the hang to exactly one init step, e.g.:
- no `I` → OpenSBI _start/assembly never reaches C (lottery or reloc hang)
- `I` but no `[` → coldboot lottery hang
- `[S` then stop → sbi_heap_init
- `[SHDMWR` then stop before `T` → sbi_timer_init (CLINT mtimer access)
- up to `R` then stop at `T`/`E` → timer/console-init region

Artifacts (in build/huaprop3/opensbi64/, untracked — extracted source tree):

After confirming the SD card was the 07-09 issue (re-seated, bootrom now fully
succeeds), the 2-core boot advances to the NEXT layer and reveals a NEW blocker:
**OpenSBI cold boot prints no banner** after the bootrom jumps to it.

Reproduced twice, both with fresh captures that stayed alive (ruling out the
earlier capture-timeout artifact):
- Build 73 diag bootrom runs to completion: `B69 DDR OK` → `B69 GPT sig=` → copies
  fw(528)/image(38831)/dtb/initrd → `B69 releasing harts and jumping OpenSBI` →
  `B69 jump fw=0000000080000000` `B69 jump dtb=0000000088000000`.
- After that jump: UART goes STATIC. 80s growth-sampling delta=0 at 35721 bytes.
  No `OpenSBI v1.x` banner, no Platform Name, nothing.
- Capture process confirmed alive during the static period.

So the bootrom handoff is correct (`a0=mhartid, a1=fdt@0x88000000, jr 0x80000000`,
identical to the 64-core Build 68/69 path), and OpenSBI's fw_jump entry bytes
match the known-good dbg21 fw. Yet OpenSBI does not reach its first `sbi_printf`
("OpenSBI v..."). That puts the hang in the OpenSBI cold-boot sequence BEFORE
console init (`init_coldboot`: scratch_init → heap_init → domain_init → hsm_init
→ hart_init → timer_init → platform_early_init[=generic_early_init→fdt_serial_init
= console]). Any of these hangs → no banner.

Difference vs 64-core (where OpenSBI boots): the OpenSBI was compiled with
`OPENPITON_DEFAULT_HART_COUNT=64` (hardcoded in openpiton.c), but this DTB
describes only 2 harts. HSM/timer/mswi structs are sized for 64. Cold-boot init
iterates per the DTB hart count, so 64-vs-2 shouldn't hang cold init by itself,
but the static `mswi.hart_count=64` / `mtimer.hart_count=64` and the 64-entry
PLIC context_map are present in the binary.

Likely cold-boot hang candidates to investigate next:
1. `sbi_hsm_init` / secondary-hart release path at 2 harts.
2. `aclint_mtimer_cold_init` / `aclint_mswi_cold_init` with hart_count=64 on a
   2-tile fabric (does it touch a CLINT register for a non-existent hart and
   stall? earlier analysis said cold_init only sets scratch pointers, but the
   memrange add and the 64-context PLIC init touch more state).
3. fdt parsing / console (uart8250) init with the 2-hart DTB.

Next step: add an OpenSBI early raw-UART probe (print a single marker before each
init_coldboot step, directly writing THR — bypassing console init) to localize

## 2026-07-09 -- KEY HYPOTHESIS: the "SD read hang" may simply be the SD card not seated in the FPGA slot

User raised the simplest possible cause of the isolated SD-read hang: **is the SD
card actually inserted / seated in the FPGA slot?** This is highly plausible and
was NOT yet excluded. Reassessing the evidence, it fits perfectly:

Timeline of the physical card:
- 2026-06-26..28: 64-core dbg21/dbg26 boots READ the SD fine (card seated in the
  P3 FPGA SD slot, same board, same slot, same SPI-SD RTL).
- Between 06-28 and 07-09: the card was removed, written with the 2-core image
  (`p3_opensbi_linux_2hart_final.img`) in a card reader, then "put back into the
  FPGA".
- 2026-07-09: 2-core boots hang at the first SD data read.

Why a missing/poorly-seated card produces EXACTLY this signature:
- `B69 DDR OK` — DDR needs no SD card. Works.
- UART prints fully — needs no SD card. Works.
- `B69 SD init OK` — MISLEADING: bootrom `init_sd()` (`sd.c:12-16`) only prints
  and `return 0`; it does NOT touch hardware or check card presence. So it prints
  OK whether or not a card is present.
- `copying block 0 of 1 blocks (0 %)` then permanent silence — this is the FIRST
  real hardware SD read (CMD17 via the SPI-SD controller for GPT LBA 1). With no
  card responding on MISO, the SPI-SD controller's command/response state machine
  waits forever, the AXI read never returns `rvalid`, the core's load never
  completes, and there is no timeout in the NoC/cache path → permanent hang.

Crucially this does NOT contradict "64-core reads SD fine": the 64-core runs used
the SAME board and SAME slot with the card seated. The only thing that changed for
the 2-core runs is the card's physical insertion state after it was pulled to
write the image. So the SD-read-path RTL is not necessarily tile-count-dependent
at all — the far more likely variable is a poorly-seated / not-clicked-in card.

## 2026-07-09 -- Static deep-dive: L1.5 WMT write-guard removed "for timing" is a concrete suspect for the intermittent stale-L1 hang

Since sim exhausts the RTL-functional coherence hypotheses (all coh_* PASS) but
the board hangs intermittently under load, I traced the ONE piece of L1.5
coherence state that (a) gates whether an invalidation reaches the L1 D-cache
at all, and (b) has an explicit "timing fix" that dropped a hazard guard: the
**Way-Map Table (WMT)**.

### Why the WMT is the linchpin of L1 invalidation

The L1.5 does not track which L1-D way holds a line directly; it keeps a WMT
(`rf_l15_wmt.v.pyv`, one entry per L1D set) mapping L1.5 line -> L1D way. When a
remote store forces an invalidation, the pipeline forwards it to the core ONLY
if the WMT lookup matches (`l15_pipeline.v.pyv:3904`):
```
`L15_CPX_GEN_INVALIDATION_IF_TAGCHECK_MES_AND_WAYMAP_VALID:
    cpx_req_val_s3    = tagcheck_state_mes_s3 && wmt_compare_match_s3;  // WMT-gated
    cpx_inval_way_s3  = wmt_compare_match_way_s3;                       // way from WMT
```
So a stale/incorrect WMT read => the invalidation is silently dropped or sent to
the wrong way => the L1 keeps a stale line => a spinning reader reads the old
value forever. That is exactly the stop_machine / XSBench symptom.

### The WMT RAM has a 2-cycle write latency and NO write-to-read bypass

`rf_l15_wmt.v.pyv`: read is `regfile[read_index]` registered (issue s2, data
s3). Write is registered TWICE: `write_valid`->`write_valid_f` (1 cyc), then the
actual `regfile[write_index_f] <= ...` on the NEXT cycle. So a WMT write decided
in s3 lands in the array **2 cycles after s3**, and the read port does not
forward the pending `write_data_f`.

### The removed guard (the concrete suspect)

`l15_pipeline.v.pyv:3776-3778`:
```
// trin: timing fix: removing guard for wmt writes; should still be correct
// l15_wmt_write_val_s3 = wmt_write_val_s3 && !stall_s3 && val_s3;
l15_wmt_write_val_s3 = wmt_write_val_s3 && val_s3;   // <-- !stall_s3 dropped
```
The WMT write now fires even while s3 is stalled. `stall_s3 = stall_for_cpx_s3
|| stall_for_noc3_s3` -- i.e. it stalls whenever the CPX (response-to-core) or
NoC3 (writeback-to-L2) channel is congested. **Under 64-core load those channels
are frequently congested, so s3 stalls are common** -- load-dependent, matching
the board behaviour and the sim's inability to reproduce (the sim's
zero/fixed-latency `fake_mem_ctrl` almost never congests CPX/NoC3).

### The hazard window (hypothesis, not yet proven)

The index-conflict guard that protects back-to-back same-set accesses only
covers the s2/s3 slots:
```
stall_index_bypass_match_s1 = (val_s2 && idx_s1==idx_s2) || (val_s3 && idx_s1==idx_s3);
```
But the WMT write completes 2 cycles AFTER s3. When s3 is stalled for multiple
cycles with the write-guard removed, the timing relationship between "when the
WMT write actually lands" and "when a following same-index request's s2 read
samples the array" shifts by the stall length. The guard reasons about pipeline
slots (s2/s3), not about the RAM's internal 2-cycle write pipe, so a stalled-s3
WMT write racing a trailing WMT read of the same index is not obviously covered.
If that read samples the array in the 1-cycle gap before the delayed write
lands, it gets stale way-map data -> wrong/dropped invalidation.

This is a **specific, code-anchored hypothesis**, NOT yet proven. It is exactly
the class the fixed-latency sim can't hit and STA can't see (functional protocol
race, not setup/hold), and it is load-gated (needs CPX/NoC3 congestion to stall
s3), which fits "passes light diags, hangs under heavy 64-core traffic".

1. Build a focused sim assertion: in `cmp_l15_messages_mon`, flag any cycle
   where `l15_wmt_write_val_s3` is high while `stall_s3` is high AND a WMT read

2. If confirmed, the fix is to restore the guard (or add a WMT write-to-read

## 2026-07-07 -- Re-analysis: "MSIP delivery to 58 harts broken" is FALSIFIED; real suspect narrows to a concurrent-IPI ordering/coherence race

Went back over the wiki logs + static evidence instead of pushing the blocked
OpenSBI probe. The prior "stop_machine IPI deadlock => 58/64 harts never get
their MSIP" root-cause statement is **over-read and internally inconsistent**.
Correcting it.

### Falsification 1: SMP bringup already proves MSIP delivery works for all 64 harts

Static: OpenSBI `sbi_hsm.c:168-186` -- a secondary hart parks in
`sbi_hsm_hart_wait` with `csr_set(CSR_MIE, MIP_MSIP|MIP_MEIP)` then `wfi()`.
It is woken **only** by an MSIP IPI (`hart_start` -> `sbi_ipi_raw_send`). So
every secondary that comes online was woken from `wfi()` by an MSIP.

Board log (dbg27, `b0369yu8y.output`): `smp: Brought up 1 node, 64 CPUs`,
`online_cpus=64`. **All 64 harts were successfully woken by MSIP.** Therefore
the CLINT MSIP -> per-hart interrupt-line delivery path is **functional for all
64 harts** -- a permanently broken wire/route to 58 harts is impossible, or
those harts would never have come online. The earlier "58 harts never respond
to the IPI" is falsified.

### Falsification 2: soft-lockup absence != "hart didn't get the IPI"

The 6 CPUs that report soft lockup are `{0,1,3,4,11,12}`. I previously read the
other 58 as "did not respond to the stop IPI". That is a misread of the
soft-lockup mechanism:

- soft lockup is a **per-CPU** watchdog: a CPU prints **only if its own timer
  IRQ is still alive** AND it has been stuck >20 s in a non-scheduling loop.
- So the 6 reporters = harts that (a) got the stop IPI, (b) entered
  `multi_cpu_stop`, and (c) still have a live timer IRQ to run the watchdog.
- The silent 58 are **not** necessarily "IPI lost". They split into: harts
  parked idle (nothing to report), harts stuck with a **dead** timer IRQ
  (can't print), or harts stuck elsewhere. Absence of a soft-lockup line
  carries almost no information about IPI receipt.

So the headline number "6/64 responded" does **not** mean "58 IPIs lost".

### What actually differs: bringup (works) vs stop_machine (hangs)

Both use the same CLINT MSIP hardware, so the bug is not the wire. The
differences that matter:

1. **Concurrency/contention.** Bringup is sequential/batched -- harts woken
   with low simultaneous NoC load. stop_machine fires IPIs to all 63 harts
   near-simultaneously **and** each acks back, a burst of concurrent MSIP MMIO
   writes + returns through the NoC/chipset CLINT bridge under contention.
2. **Privilege/MMU state.** At bringup the target sits in M-mode `wfi`. At
   stop_machine the target runs S-mode Linux with the MMU on; the IPI must be
   taken as M-mode MSIP, reflected to S-mode SSIP (`sbi_ipi_process` ->
   `csr_set(MIP, MIP_SSIP)`), and delivered through Linux's irq path. More
   stages, more shared state.
3. **Shared-memory sync, not just the interrupt.** `multi_cpu_stop` is a
   spin-loop state machine over a **shared `multi_stop_data` struct** in DRAM:
   every hart must SEE the state advance (MULTI_STOP_PREPARE -> DISABLE_IRQ ->
   RUN -> EXIT) written by the leader. This is exactly the cross-hart
   shared-writer visibility that the silent MMIO-read coherency barrier (dbg21)
   was patching. If a hart's view of `msdata->state` is stale, it spins forever
   even though its IPI arrived fine.

### The strongest under-weighted lead: the sim DID reproduce an L1.5 anomaly on the IPI/sync path

`coh_ipi64.c` on the 8x8 Verilator model produced an intermittent
`cmp_l15_messages_mon` failure -- an L1.5 DTAG/protocol anomaly around a TILE0
store at `0x8020e9c`, on the IPI/sync path. It was later demoted to a "stale
lead" only because a low-overhead *progress-only* sweep didn't re-trip the
monitor in 3 runs -- that is weak evidence of absence (the monitor prints were
suppressed for speed, and the fail is intermittent). Crucially, `coh_64core`
(AMO/store broadcast) did **not** trip it, but `coh_ipi64` (MSIP + tight
cross-hart sync) did -- the anomaly is specific to the interrupt/sync pattern,
which is exactly `multi_cpu_stop`.

### Revised root-cause hypothesis (ranked)

1. **Cross-hart shared-memory ordering/visibility race in `multi_cpu_stop`'s
   `msdata->state`** (a coherence/ordering problem on the sync variable, NOT a
   lost interrupt). Fits: bringup works (little shared spinning) but
   stop_machine hangs (tight shared spin); dbg21 needed an MMIO-read barrier
   for exactly this class; the `coh_ipi64` L1.5 anomaly is on this path;
   intermittent + timing-dependent; XSBench unionized-grid (heavy shared
   sync) hangs the same way.
2. **Concurrent-IPI ordering bug** in the CLINT bridge / `sbi_ipi` fast-path
   under a simultaneous 63-way storm (e.g. the `__atomic_fetch_or(ipi_type)`
   "only send if was 0" optimization dropping a needed re-send when an ack and
   a new send race). Lost/merged IPI, but only under the storm.
3. **Timer IRQ death on the stuck harts** (the silent 58 include harts whose
   timer stopped), making it look like more harts are stuck than the 6 that can
   still print.

### Why this matters / next step

The blocked OpenSBI MSIP write+readback probe was testing hypothesis "MSIP
doesn't reach CLINT" -- which Falsification 1 already makes unlikely. Higher
value now:

- **Re-run `coh_ipi64` with the messages-monitor fail branch actually
  instrumented** (compact context print on the real `MONITOR_PATH.fail`), loop
  until it trips, and capture a narrow VCD of the TILE0 L1.5 `0x8020e9c`
  DTAG/MESI transition + the CLINT MSIP return flit. This directly tests
  hypothesis #1/#2 in sim, no board churn, no OpenSBI rebuild.
- Alternatively, a board-side software test that is decisive without ILA:
  a tiny kernel module / bare-metal loop that hammers `multi_cpu_stop`-style
  all-to-all IPI + shared-flag spin and counts which harts fail to observe the
  flag (distinguishes "IPI lost" from "shared read stale").
- ILA on CLINT `msip_q[63:0]`/`ipi_o[63:0]` remains the hardware-truth
  fallback, but it tests the *least* likely hypothesis first, so it is not the
  cheapest next step.

Bottom line: the failure is most likely a **cross-hart shared-memory
ordering/coherence race on `multi_cpu_stop`'s sync state under concurrency**,
not a broken per-hart MSIP wire. This also re-opens the question of whether the
dbg21 MMIO-read barrier is truly sufficient at 64 cores or just shifts the race

- `clint.sv` (ETH Zurich design) is standard: shared `mtime`, per-hart
  `msip`/`mtimecmp`, `MSIP_BASE`/`MTIMECMP_BASE` decode indices
  (`address[7:2]` / `address[8:3]`) correct for `NR_CORES=64`. `ipi_o=msip_q`
  (registered level), `timer_irq_o` combinational `mtime>=mtimecmp` (level,
  re-sampled by the core synchronizer).
- Interrupt distribution is **direct wiring, not a network**: chipset
  `timer_irq_o[63:0]`/`ipi_o[63:0]` -> `chip.v.pyv:152` -> each tile consumes
  its own bit (`chip.tmp.v:3689 .timer_irq_i(timer_irq_i[0])`). No NoC, no
  arbitration, no serialization -> if CLINT asserts `ipi_o[h]`, tile h WILL see
  it (after the 2-flop synchronizer in `ariane_verilog_wrap.sv:156-181`).
  Core-side wake-up interrupt workaround is commented out; the active gate is
  just a 32k-cycle SRAM-init reset delay.
- `noc_axilite_bridge.v` (every CLINT/PLIC/UART/bootrom MMIO write): correct
  single-outstanding AXI-lite FSM; AW/W/B status tracked separately and
  combined; load/store ACK arbitration is fair.
- `rv_plic_gateway.sv` (lowRISC): standard edge/level `ip`/`ia` logic.
- `rtc`/`mtime`: `system.v:601 assign rtc = rtc_div[6]` -- synchronous 7-bit
  divide-by-128 of `core_ref_clk`, registered (no glitch); CLINT resynchronizes
  via 2-stage `clint_sync_wedge`. timebase matches DTB.

**Decisive architectural finding -- no request timeout:**
`grep -riE "timeout|watchdog"` over `tile/l15/rtl`, `tile/l2/rtl`,
`tile/dynamic_node/rtl`, and `wt_l15_adapter.sv` returns **zero** matches in
the synthesized logic. The only hit, `corev_apu/tb/.../sim_timeout.sv`, is a
**testbench** `$fatal` watchdog -- which exists precisely because the design
can hang forever. L2 (`l2.v`, `l2_pipe1.v`, `l2_mshr.v.pyv`) has 0 timeouts.
**Consequence:** an L1.5/L2 MSHR that allocates for a miss and never receives
its fill/response stays PENDING forever -> **silent permanent hang, no trap,
no log, no error**. The architecture assumes the NoC is perfectly reliable.

**Why this redirects the root cause:**
The observed symptom -- intermittent, SAME image sometimes boots fully,
sometimes silently stalls at `[0.000000]`; single-thread XSBench also hangs;
stop_machine also deadlocks; all with zero UART growth and no panic -- is
exactly the signature of **an intermittently dropped/misrouted NoC response
(memory fill or MMIO ack) becoming a permanent silent hang because there is no
timeout**. The timer EPC captured earlier is incidental (timer interrupts keep
firing; the trap state happens to land at the softirq IRQ-enable boundary).
This is NOT 64-core-specific -- a single core doing heavy memory traffic can
hit it. The failure mode is the memory/IO response path, not the timer logic.

**Highest-value next probe (cheap, deterministic in sim):** add an
MSHR-stall watchdog to the Verilator harness -- sample the L1.5
outstanding-request signal and dump VCD + the stuck address the first time a
request stays outstanding > N (e.g. 10000) cycles. Run a single-hart memory-
stress diag that mimics XSBench's pattern (large working set, pointer chase,
cache thrashing) rather than the simple store-load of `coh_*.c`. The watchdog
fires deterministically the moment a response is dropped, localizing the drop
to a specific address / NoC route. This beats blind 8x8 VCD sweeps.

## 2026-07-03 -- OpenSBI timer path deep-dive: code is CORRECT — corruption is in kernel timer DATA

### Crash disassembly analysis

The crash EPC `0xffffffff807fa154` (`__do_softirq+0x9e`) disassembles to:
```asm
ffffffff807fa154:  000d879b    sext.w  a5, s11   # sign-extend register, NOT a load
```

**Key corrections from earlier analysis:**
- `cause = 0x8000000000000005`: bit 63 SET → this is a **S-mode timer INTERRUPT**, not a Load Access Fault (which would be cause=5 without bit 63).
- `badaddr = 0xd879b`: for interrupts, sbadaddr is not updated. This value (= the instruction encoding `0x000d879b`) is **stale/garbage** — the trap frame itself may be corrupted.
- The EPC instruction (`sext.w`) cannot fault — confirming the crash state is corrupted.

### OpenSBI timer code review: all correct

Reviewed `sbi_timer.c`, `aclint_mtimer.c`, `fdt_timer_mtimer.c`:

1. **mtimecmp write**: 64-bit atomic MMIO (`writeq_relaxed`, single 64-bit write). OpenPiton CLINT has `has_64bit_mmio = true`. No split-write race.
2. **Per-hart mtimecmp**: `time_cmp[target_hart - mt->first_hartid]` with `target_hart = current_hartid()` (reads `mhartid` CSR). Correct hart indexing.
3. **Per-hart timer state**: `timer_state` in per-hart scratch, spinlock-protected. No cross-hart data race in OpenSBI's timer management.
4. **STIP forwarding**: `csr_set(CSR_MIP, MIP_STIP)` in the callback. Standard M→S timer delegation.
5. **dbg21 barrier**: runs only on non-IRQ traps (ecalls). Timer interrupts are IRQs → barrier does NOT interfere with timer path.

**Conclusion**: OpenSBI's timer code is standard, well-tested, and correct for 64 harts. No bug found.

### Where the corruption actually is

The crash is in **Linux's kernel timer softirq data structures** (hrtimer bases, timer lists, per-CPU timer data). The corruption propagates from an unknown source into the kernel's linked list / per-CPU data, and the timer interrupt handler crashes when it traverses the corrupted structures.

Possible corruption sources (not yet confirmed):
1. **Subtle coherency corner case**: coh_64core proved basic store→load visibility works, but kernel timer linked lists involve complex pointer-chasing patterns (READ_ONCE/WRITE_ONCE across cache lines, per-CPU locks, cross-CPU timer delegation). A subtle invalidation miss on a specific access pattern could corrupt list nodes.
2. **Kernel SMP bug at 64 cores**: Linux's per-CPU timer management might have a scaling issue (e.g., per-CPU data alignment, TLB pressure, or a race in the timer wheel at high core counts).
3. **NoC/memory subsystem**: intermittent data corruption during heavy 64-core memory traffic (unlikely but not ruled out).

### Next investigation targets (not yet started)
1. Test with fewer cores (2x1, 4x4) — if crash doesn't reproduce, it's 64-core-specific.
2. Add kernel-side instrumentation to the timer softirq (check list integrity before traversal).
3. Try `nohz_full` (disable timer ticks on non-boot cores) to see if the crash goes away.
4. Kernel config: `CONFIG_HZ=100` → `CONFIG_HZ=10` (reduce timer tick frequency) to see if crash frequency changes.
