  seed 0 and decoded the older `23535xxx` TILE36 event. The access is an

- The TILE36 CSM state at `23535250` is a read-only path:

  `TILE36 L15_CSM REQ MON` / `SIGDIE` line was caused by a BootROM or CLINT
  device response being misclassified as a CSM/HMC fill. The next root-cause
  capture must trigger on the actual messages-monitor fail condition rather
  than the last high-volume monitor line printed before abort.

Programmed Build 68 PDI (DONE bit: HIGH, 4 ILAs) + dbg26 SD image (dbg21 fw + corrected DTB initrd-end 0x90107d9c + XSBench rootfs v2). UART capture (72113 bytes, ev_retry.log, saved at /tmp/uart_64core_shell_evidence.log). The full layer chain:

2. **bootrom** -- `B68 OpenSBI bundle bootrom` + `B68 jump fw=0000000080000000 dtb=0000000088000000`.
3. **OpenSBI** -- banner + SBI TIME/IPI/RFENCE extensions detected.
4. **Linux kernel** -- `Linux version 6.6.0 ... #5 SMP Fri Jun 12 14:31:03 CST 2026`.
5. **64-CPU SMP bringup** -- all 64 harts brought up (calibrated).
6. **Interactive shell** -- init script output: `nproc=64`, `cpuinfo_processors=64`, `=== P3_64CORE_SHELL_READY ===`, `~ #` prompt.

This is the **first one-hand UART log** proving an interactive 64-core shell with `nproc=64`. Prior "64-core shell achieved" claims in older devlog entries were based on expired/truncated captures and are now superseded by this evidence.

### Intermittent early-Linux stall confirmed

Run 1 (same PDI/SD): stalled at `[0.000000] OF: reserved mem: mmode_resv0@80000000` (39517 bytes, zero growth). Run 2 (reprogram): reached the full shell (72113 bytes). The forward-progress stop at Linux `[0.000000]` is **intermittent** -- the same combination sometimes stalls before SMP bringup, sometimes succeeds all the way to the shell.

### Shell interactivity verified

Sent commands via slow per-character UART write; shell echoed them back (garbled due to keep_bootcon double-printing + interleaving). The init script output (`nproc=64` + `cpuinfo_processors=64`) is authoritative and does not depend on interactive UART reliability.

## 2026-07-03 -- 64-thread XSBench ACTUALLY RUNS but HANGS during unionized grid init

### First real XSBench execution on 64-core Linux (not a misattribution)

On the confirmed 64-core shell (this session's P3_64CORE_SHELL_READY), ran `/root/XSBench -s small -l 100000` with 64 threads (OMP_NUM_THREADS=1 did not take effect; XSBench reported `Threads: 64`).

XSBench output summary (from UART log):
- H-M Benchmark Size: small
- Total Nuclides: 68
- Unionized Energy Gridpoints: 768,604
- Particle Histories: 500,000
- Total XS Lookups: 100,000
- Threads: 64
- Est. Memory Usage: 241 MB

### Freeze point: unionized grid initialization -> complete system hang

XSBench progressed through "Intializing nuclide grids..." then started "Intializing unionized grid..." and FROZE. Zero UART growth after that. Shell unresponsive (sent `echo P3_CHECK`; UART echoed the command but no output returned -- the entire Linux system hung, not just XSBench).

The unionized grid init is heavy parallel compute (sorted merge of 768K energy gridpoints across 64 threads). This is consistent with the intermittent Linux forward-progress stop seen during boot (stop_machine deadlock at ~32s, and `[0.000000]` stall) -- heavy SMP compute triggers a system-level hang.

### Next: single-thread XSBench to isolate

Need to reprogram + retry with `OMP_NUM_THREADS=1` actually enforced. If single-thread XSBench completes, the hang is specific to multi-threaded parallel compute (the 64-thread shared-write/sync path).
