## 一、本周目标

1. 用单变量 A/B 实验确定"Linux 6.6 无法打印 banner"是固件/硬件问题还是内核版本问题。

## 四、本周新问题与根因

### A. Linux 5.1 A/B 实验隔离出内核版本专属 blocker

- **实验设计**：保持 OpenSBI v1.8 固件、1-hart DTB、initramfs 和 Build 66 PDI 完全不变，仅将 Linux 6.6 Image 替换为 Linux 5.1.0-rc7 `payload.bin`。
- **结果**：Linux 5.1 打印 banner、初始化内存（2 GiB DDR）、注册 RISC-V 定时器时钟源、上线 1 CPU、初始化 devtmpfs/网络/USB/RPC-NFS/`piton_sd` 驱动，达到 `Run /init as init process`。
- **ext2 rootfs 变体**：换成 ext2 根文件系统后进入真正用户空间（`Starting logging: OK`、`Starting rpcbind:`）。Linux 6.6 在同一固件和硬件上连 banner 都无法打印。
- **结论**：OpenSBI 固件层、硬件-固件契约（timer、PMP、MIDELEG/MEDELEG、中断委派）和 bootrom/SD/DDR 路径全部功能正常。Linux 6.6 启动失败是内核版本专属的——由 Linux 6.6 早期 S-mode 入口代码、内核配置或其与 OpenSBI 的交互引起，不能归因于固件或硬件。

### B. OpenSBI FDT 重定位覆盖 SD DTB——已闭环根因

- **现象**：内核报告 `Kernel command line: earlyprintk`（`CONFIG_CMDLINE` 默认值），并报告 `initrd not found or empty`，说明完全未读到 DTB 中的 bootargs、UART、CLINT、PLIC、SD 和 initrd 属性。
- **根因**：Build 66 bootrom 的 `startup.S` 将 a1 设置为其内嵌 DTB 地址（bootrom 空间 ~`0xFFF101xxxx`），该 DTB 只包含 memory 和 cpus 节点。OpenSBI `fw_base.S` 冷启动 FDT 重定位步骤比较 `fw_next_arg1()` 返回值（`0x81600000`，完整 DTB 所在地址）与 bootrom 传入的 a1；两者不同时，OpenSBI 将 bootrom 最小 DTB 复制到 `0x81600000`，覆盖完整 DTB。
- **修复**：在 `fw_jump_p3_64core.bin` 偏移 `0x286` 处二进制补丁一条指令，将 `beq t1, a1, _fdt_reloc_done`（`0x04b30063`）改为 `beq zero, zero, _fdt_reloc_done`（`0x04000063`），使 FDT 重定位无条件跳过。
- **验证**：补丁后内核报告完整命令行 `earlycon=uart8250,mmio,0xfff0c2c000,115200n8 console=ttyS0,115200n8 rdinit=/bin/sh init=/bin/sh`。

### C. OpenSBI/Linux 5.1 交互 shell 与 XSBench 运行——全链闭环

- **集成镜像**：使用 noreloc OpenSBI、未改 Linux 5.1 `payload.bin`、完整生成的 1-hart P3 DTB（含 UART/PLIC/CLINT/SD/2 GiB memory/234375 Hz timebase/bootargs/精确 initrd 范围）、从 `payload.bin` 提取的 Linux 5.1 内置 initramfs（替换不相关的外部 userspace）。
- **shell 证据**：`Run /bin/sh as init process` 后，BusyBox 打印 `can't access tty; job control turned off` 和 `/ #` 提示符。逐字符 200 ms UART 输入执行 `echo P3_SHELL_OK` 回显成功；`uname -a` 返回 `Linux ariane-fpga 5.1.0-rc7 ... riscv64 GNU/Linux`；`nproc` 和 `/proc/cpuinfo` 均报告 1 CPU。
- **XSBench 证据**：双分区镜像（ext2 第二分区装载 XSBench），板级运行 `/mnt/XSBench -s small -p 1000 -l 1` 完成。报告 `Particle Histories: 1,000`、`Simulation complete`、`Lookups: 1,000`，运行时间 0.585 秒。校验和警告 2972 是因为非默认 `-p 1000 -l 1` 参数不在 XSBench 内置参考表中，不影响执行正确性。
- **纠偏**：之前"shell 已运行、UART RX/PLIC 中断委派是根因"的声明被撤回。控制重测（逐字符 200 ms 输入、单 reader、raw/no-echo 配置）在 30 秒窗口内未出现 BusyBox 提示符也未回显命令。真正的问题是 boot-payload/userspace 集成缺陷（外部 initramfs 覆盖了正确 userspace），不是 UART RX。同一 OpenSBI 路径在有正确 userspace 时正常接受 UART 输入。

### D. Linux 6.12.98 MPI 系统基线建立——系统原语验证通过

- **新 `piton_sd` 驱动**：从 SDK 源协议（`0099-Piton-SD-Driver.patch`）移植到 Linux 6.12 `submit_bio`/`blk_alloc_disk` API。自旋锁串行化同步 SD MMIO 操作，消除原驱动的多 hart 竞争。
- **系统配置**：`CONFIG_NR_CPUS=64`（为后续 2/64 hart 扩展准备）但 DTB 仅暴露 CPU0；启用 FPU、futex、CPU 亲和性、SysV/POSIX IPC、共享内存、mqueue、Unix/TCP socket、block/GPT/ext4、`piton_sd` 驱动；保持 `CONFIG_BLK_DEV_LOOP=n`（generic defconfig 在未用的 `loop_init` 中停止）。
- **集成缺陷修复**：
  - `CONFIG_BINFMT_SCRIPT` 未设置，导致 `/init`（BusyBox shell 脚本）返回 `ENOEXEC`（error -8）。修复后在 `olddefconfig` 后强制断言。
  - `/init` 未置起 loopback，导致 TCP loopback 测试返回 `errno=99`（EADDRNOTAVAIL）。修复后在 smoke 之前自动 `ip link set lo up`。
- **板级证据**：OpenSBI v1.8 报告 1 hart、234375 Hz mtimer；Linux 6.12.98 打印 banner、完成所有 initcall、注册 `/dev/piton_sd1`（524288 sectors = 256 MiB）、达到 `Run /init as init process`；自动 `P3_MPI_SYS ALL_PASS failures=0`；进入 BusyBox `/ #` 提示符。
- **系统原语覆盖**：CPU 亲和性、`CLOCK_MONOTONIC`、pthread/futex、`fork` 后共享匿名内存、POSIX mqueue、Unix socket、TCP loopback 全部通过。这是 MPI 运行时所需的内核/系统调用就绪性 gate，但不等于 MPICH/OpenMPI 本身已安装或执行。

### E. Linux 6.12 PID 1 exec 入口阻塞——当前未解决的核心问题

- **现象**：Linux 6.12 shell 可交互，但自动 `/init` 或 `/root/XSBench` 在 `Run /init as init process` 和 `TERM=linux` 环境行之后不再产生任何 UART 输出。手动 XSBench 运行 15 分钟无输出、无返回，Ctrl-C 无法恢复。
- **ILA 证据**：Build 66 现有 4 个 ILA 显示核心有心跳（heartbeat 在 toggling）、无 L1.5/DDR 错误、无活跃 core/L1.5 或 DDR 握手、timer 和外部中断输入 pending。但这些 ILA 不暴露 commit PC、中断使能或特权状态，不能定位具体指令。
- **UART vector 稳定性**：多次运行中 UART vector `0x179f807e34c0000b` 字节一致，但该 vector 在 `P3_BD_UART_RW_DEBUG_ILA` 模式下是 retained last-completed data/address 字节，不是默认 live AXI-valid/ready 布局。之前基于该 vector 的 live-handshake 解码和 UART AXI 死锁声明无效。
- **XSBench stage marker 诊断**：在不改变内核的前提下，在 XSBench 源码中插入直接 `write(2)` 标记器（不经 stdio/heap）。板级运行停在 `TERM=linux` 环境行，未出现任何 `P3_XS` 标记——包括构造函数标记 `P3_XS M-1`。
- **观察性边界纠正**：UART 标记缺失不能证明 CPU 未继续执行 `/init` 公共序言或后续 XSBench。控制台/UART 路径丢失本身就是一个高优先级假设。因此单靠 UART-only 标记方案不足以定位当前 recurrent 停点。
- **持久化 PID 1 诊断**：设计了 UART 无关的诊断方案——PID 1 在每个 stage 用独立的 512-byte sector 写入持久记录到 SD 第二分区（`/dev/piton_sd2`），使用 `P3STG1` 头、单调时间和 FNV-1a 校验和。每个 stage 先 fork 非阻塞持久 writer child 和独立 console/`/dev/kmsg` writer child，父进程永不等待观察者。
- **持久化结果**：两次板级运行（原始 PID 1 和 pre-fork marker 变体）后，完整的 1 MiB 诊断分区 SHA-256 与镜像打包时字节一致（`9b78565275913bee...`）。这比 UART 文本缺失更强：没有任何 PID 1 stage 完成持久写入，包括 MPI smoke 和 XSBench。
- **ILA 非重置快照**：无 SD 读写事务活跃（SD transaction manager 和 AXI bridge 均在 `RDY`）、无 L1.5 或 DDR 错误、无活跃 L1.5/DDR 握手。sticky last L1.5 请求地址 `0x804e0c30`/`0x804e2aa0` 映射到 Linux per-CPU `runqueues` 对象，与 fork/scheduler 边界一致但不构成根因。
- **当前结论**：PID 1 在 `kernel_execve()` 或更早的 exec 路径中阻塞。诊断分区原始空白排除了 UART-only 解释。现有 ILA 不暴露 `kernel_execve`、用户 PC、syscall PC、特权或 block-layer 等待状态。

### F. 内核 exec trace 检查点——下一步诊断方案

- **设计**：在 Linux 6.12.98 的 `fs/exec.c`、`fs/binfmt_elf.c`、`arch/riscv/kernel/process.c` 中插入 21 条 `pr_emerg("P3KEXEC Kxx ...")` 检查点：
  - K10-K30：`kernel_execve` 入口/参数准备
  - K40-K44：`bprm_execve` 凭据/调度/exec_binprm
  - K50-K51：`search_binary_handler` load_binary 前后
  - K60-K71：`load_elf_binary` ELF 加载全流程
  - K80-K81：`start_thread_enter/return`
  - K90-K91：RISC-V `start_thread` 寄存器设置
- **构建**：增量编译仅受影响的 3 个对象文件（exec.o、binfmt_elf.o、process.o）。新内核 Image SHA-256 `baecca0f94c679c5...`。
- **镜像**：exec trace 镜像已构建、哈希校验、压缩传输、写卡和回读验证完成。所有其他组件不变（OpenSBI noreloc、DTB、PID1 诊断、XSBench markers、Build 66 PDI）。
- **预期**：最后一个出现的 Kxx 标记将精确区分 ELF 映射/栈构造阶段与用户寄存器状态提交后的丢失。

## 五、方法论与纠偏

1. **Linux 5.1 A/B 是本周最有效的隔离工具**：在同一固件/硬件/DTB 下仅替换内核 Image，直接证明 blocker 在内核版本而非硬件。后续应优先使用已知可工作的版本做单变量控制。
2. **FDT 重定位是"固件覆盖 DTB"的经典 pitfall**：OpenSBI 默认行为假设 bootrom 传入的 a1 是"正确的" FDT。在 P3 Build 66 的 bootrom 契约下，这个假设不成立。二进制补丁虽然能解决问题，但长期应考虑在 OpenSBI 配置层面禁用 FDT 重定位。
3. **UART RX 根因声明撤回的教训**：`Run /init as init process` 在 exec 之前打印，不等价于 shell 已运行。在没有 BusyBox 提示符（`can't access tty` 或 `/ #`）的情况下，不能声称 shell 在工作。
4. **UART 标记缺失不能等于执行缺失**：控制台/UART 路径丢失本身是假设。持久化诊断分区（SD-backed，独立于 UART）是区分"CPU 真停"和"console 无输出"的正确手段。
5. **压缩传输是强制要求**：用户明确要求所有镜像传输采用压缩方式。已写入 AGENTS.md：只用 `.img.gz` 压缩 artifact，远端校验压缩 SHA-256 和解压 raw SHA-256 后才写入。
6. **增量构建优先**：内核级补丁只需增量重编受影响的对象文件，不需要全量 rebuild。已写入 AGENTS.md。

## 八、对 P0-P4 路线图的影响

- **P0/P1 单核基线**：Linux 5.1 全链闭环证明了 OpenSBI 启动路径的可行性。Linux 6.12 达到了 MPI 系统原语就绪性。当前的单核 blocker 是 PID 1 exec 入口，不是 boot/SD/DDR/timer/固件层问题。exec trace 检查点将精确定位。
- **P2 双核扩展**：Linux 6.12 内核已构建 `CONFIG_NR_CPUS=64`，DTB 当前仅暴露 CPU0。待单核 PID 1 闭环后，切换到 2-hart DTB 和匹配 PDI 即可回归双核测试。
- **P3 64 核 Linux**：`piton_sd` 驱动已加入自旋锁串行化，为多 hart 安全访问 SD MMIO 做好准备。MPI system smoke 验证了 `fork` 后共享内存、mqueue 和 socket 原语——这些是 OpenMPI/MPICH 运行时的系统依赖。
- **P4 千核目标**：本周证明了从 OpenSBI 到 MPI 系统原语的完整软件栈可以在单核上工作。Linux 6.12 内核大小 4.3 MiB（MPI 配置）或 2.6 MiB（精简配置），具备 FPU、SMP、IPC、网络和 `piton_sd` 支持。XSBench 在 Linux 5.1 上的成功运行验证了从内核到浮点计算应用的端到端路径。
