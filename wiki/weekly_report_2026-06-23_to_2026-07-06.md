## 四、技术深度：核心根因与发现详解

### 1. 7 个 OpenSBI coldboot 根因（dbg13→dbg21 一次性清除）

| # | 根因 | 修复 |
|---|------|------|
| 1 | Ariane 缺 `mhpmevent` CSR（写它 → 非法指令 trap） | `mhpm_mask=0` |
| 2 | OpenSBI PIE 自重定位在 P3 失败（GOT 停留链接地址） | non-PIE build（Makefile `-fno-pie`/`-no-pie` + `fw_base.ldS` 基址 0x80000000） |
| 3 | `openpiton.c` 硬编码 `HART_COUNT=3`（64 核沉默陷阱） | `HART_COUNT=64` + plic `context_map` 扩 64 项 |
| 4 | `plic_data = plic` 432 字节柔性数组结构体拷贝溢出（覆盖 `ra`） | 去掉栈 local，直接解析进静态 `plic` |
| 5 | PMP memrange power-of-2 切碎 >16 entry | allow-all PMP fallback |
| 6a | DTB 缺 `linux,initrd-start/end` | 添加 initrd 属性 |
| 6b | coherency barrier 计数耗尽（dbg18 冻 28s） | limit 2000→2000000 |
| 7 | 64 核 L2/NoC coherency ordering race | silent MMIO-read barrier（每 ecall 读 UART LSR `0xfff0c2c005`，uncached 全局序屏障） |

### 2. `stop_machine` IPI 死锁（dbg27 决定性证据）⭐

- 64 核 boot 到 32s `clocksource_done_booting` 后挂死。
- soft lockup dump：`Stopper: multi_cpu_stop <- stop_machine_cpuslocked`，`epc: __do_softirq+0x9e`。
- **64 个 hart 全部 online**（23.9s `smp: Brought up 1 node, 64 CPUs`），但**只有 6 个（{0,1,3,4,11,12}）进入 `multi_cpu_stop` 忙等** → 58 个没响应 stop_machine 的唤醒 IPI。
- SBI ecall 全成功（UART log 无 `__sbi_send_ipi_v02` 错误）→ OpenSBI 确实写了 64 个 MSIP，但 58 个 hart 没收到中断信号。

### 3. `__do_softirq+0x9e` EPC 谜团解开

- 反汇编 `__do_softirq`：crash EPC `+0x9e` 的前一条是 `csrsi sstatus,2`（开 S-mode 中断），EPC 指向 `sext.w a5,s11`（纯寄存器操作，不访存，永不 fault）。
- 真相：migration 线程在 `multi_cpu_stop` 忙等时，timer 中断照常进来（**timer 无辜**），中断退出走 `__irq_exit_rcu → __do_softirq`，EPC 落在 softirq 入口（`csrsi sstatus,2` 的下一条）——**是中断返回地址，不是故障点**。之前几周误读为"timer 数据结构崩溃点"，纠正。

### 4. 两个一度当成根因的误诊，主动纠正

- **L1 coherence**（06-25 `wt_l15_adapter.sv:121 = '0'）：当时静态推断 L1 invalidate 路径断。**07-01 纠正**：`coh_2core.c`/`coh_64core.c` 都 PASS，`wt_l15_adapter.sv:121` 那行是** outgoing** core-initiated invalidate（未用），不是 incoming snoop；真正的 incoming 路径（`L15_EVICT_REQ→DCACHE_INV_REQ`）完整 wired 且工作。
- **kernel timer 数据损坏**（07-04 之前）：crash EPC 在 `__do_softirq` 被当成 timer 链表遍历崩溃。**纠正**：EPC 是中断入口边界；`CONFIG_DEBUG_LIST/SG/PLIST=y` 会抓链表损坏但无 warning；失败间歇（同 image 时好时坏）→ 确定性软件 bug 必然每次必现 → 不可能是内核 timer 数据损坏。

### 5. "无请求超时"架构——静默挂死的放大器

- `grep timeout|watchdog` 在 `tile/l15`、`tile/l2`、`dynamic_node`、`wt_l15_adapter` 全**零命中**（唯一 hit 是 testbench `sim_timeout.sv`，它存在正说明设计能无限期挂）。
- 后果：L1.5/L2 MSHR 一旦为 miss 分配、收不到响应，**永久 PENDING → 静默永久挂，无 trap、无日志、无栈**。
- 这解释了所有失败模式都是**静默挂死**（boot stall / stop_machine / XSBench freeze），而不是带栈的崩溃。

### 6. SBI-IPI→CLINT MSIP 静态全链路审查（全对）

逐段验证 Linux `stop_machine` → SBI ecall → OpenSBI → CLINT MSIP → 中断分发 → tile 链路：
- Linux `__sbi_send_ipi_v02`（`sbi.c:238`）：per-CPU ecall，`hmask=1, hbase=cpuid_to_hartid_map(cpu)` ✓
- OpenSBI `sbi_ipi_send_many`（`sbi_ipi.c:118`）：`weight==count` 校验通过 ✓
- OpenSBI `mswi_ipi_send`（`aclint_mswi.c:44`）：`writel_relaxed(1, msip[hartid-first])` ✓
- OpenSBI `sbi_ipi_process`（`sbi_ipi.c:259`）：`raw_clear→xchg(ipi_type,0)→loop`（不丢位）✓
- DTB `cpu@N reg=<N>`（hartid 0..63 连续）+ chip 层 `ipi_i[63:0]` 64 tile 全连 ✓
- 结论：**静态代码全对，bug 在 runtime**——MSIP 写了但 58/64 hart 没收到中断信号。

### 7. dbg28 探针受挫与一连串误判（已查清）

- 目标：在 OpenSBI `openpiton.c` final_init 加 MSIP 写+回读探针，判别"MSIP 写到达 vs 中断线断"。
- 结果：OpenSBI 连 banner 都不出（挂死）。
- 误判序列（均已纠正）：
  1. 误判 gcc 版本（dbg21 远程 gcc 17 vs 本地 11.4）→ **纠正**：wiki 铁证 dbg21 就是本地 `riscv64-linux-gnu-gcc` 11.4 编的（`fw_jump.elf` `.comment` + devlog 2026-06-17 line 703）。
  2. 误判 PIE（忘了禁 PIE）→ **纠正**：Makefile 有 `-fno-pie` hack（dbg21 时加的，持久），今天编的也是 `Type=EXEC` non-PIE。
  3. 真正嫌疑：probe 的 includes（`riscv_io.h` 等）破坏了 openpiton.c 编译，或今天编的 fw 含 dbg21 后的源码改动残留。
- 教训：**先查 wiki 再下结论**——gcc/PIE 的答案 wiki 里早有，浪费了多轮 SD/XVC 迭代。

## 五、方法论亮点

1. **板上分层证据链**：编程→DONE bit→UART→bootrom→DDR→SD→OpenSBI→Linux→SMP→shell，逐层证明不跳步；每一层都有独立证据才下结论。
2. **bootargs 让挂有声**（dbg27）：加 `softlockup_panic=1 rcu_cpu_stall_timeout=10 panic_on_warn=1 watchdog_thresh=10`，把"静默永久挂"变成 soft lockup dump + 栈——零综合（只改 DTB）就抓到 stop_machine 死锁铁证。
3. **静态优先**：反汇编 `__do_softirq`（解开 EPC 谜团）+ 源码审查 SBI-IPI 全链路（排除代码 bug）+ `grep timeout`（发现无超时架构），减少昂贵的 SD/XVC 迭代。
4. **R1 wiki 同步**：每个根因/发现/纠偏即时写 devlog + commit + push（两周 25+ 次 wiki 提交），保证可追溯、可纠错。
5. **诚实纠偏**：主动纠正 L1 coherence、timer 损坏、gcc/PIE 等误诊，记录在 devlog 不掩盖——这是这两周最有价值的方法论进步。

## 八、对 P0–P4 路线图的影响

- **P3（8×8 / 64 核）**：核心打通到 Linux shell，但 **stop_machine IPI 死锁阻塞 XSBench**。这是 64 核规模才暴露的中断投递可靠性问题（2 核/单核不复现，`coh_2core`/`coh_64core` 简单 store-load 都过，但 Linux 并发 stop_machine IPI 风暴下 58/64 丢失）。
- **P4（1024 核）**：IPI 投递可靠性是关键障碍——64 核就有 58/64 不响应，1024 核会更严重。必须先解决 CLINT MSIP 经 NoC→chipset 的中断投递可靠性（或换中断机制），才能往更大规模推。
- **Quicksilver**：需可靠的多核 IPI + 收敛才能跑并行 benchmark。当前阻塞在 IPI 死锁。
