## 三、这两周新遇到的问题（现象 / 根因 / 机理 / 修复）

### A. OpenSBI coldboot 收尾（dbg13 → dbg21，3 个新根因）

#### A6a. DTB 缺 `linux,initrd-start/end` → "Unable to mount root fs"
- **现象**：Linux 起来后 `VFS: Unable to mount root fs` panic。
- **根因**：DTB `chosen` 节点缺 `linux,initrd-start`/`linux,initrd-end` 属性，Linux 找不到 `0x90000000` 的 initramfs。
- **机理**：没有 initrd 边界，内核不解析 initramfs，无法挂载 root。
- **修复**：在 DTB `chosen` 加这两个属性（指向 initrd 加载地址 + 大小）。

#### A6b. coherency barrier 计数耗尽 → dbg18 冻在 28s `clocksource_done_booting`
- **现象**：dbg18（counter-gated barrier，前 2000 个 non-IRQ trap 触发）跑到 `[28s] clocksource_done_booting` 冻结。
- **根因**：barrier 计数上限 2000 太小。
- **机理**：64 核 boot 需要远超 2000 个 ecall/trap 来提供 coherency ordering；barrier 在 28s 后停止 → 后续 trap 无全局序屏障 → coherency race → 冻。
- **修复**：limit 2000→2000000（dbg20/dbg21），覆盖整个 boot + runtime。

#### A7. 64 核 L2/NoC coherency ordering race → silent MMIO-read barrier（dbg21 到 shell 的最终修复）
- **现象**：即使上周报的 5 根因全修 + A6a/A6b 修，64 核 boot 仍偶发 coherency 违例（stale L1 读）。
- **根因**：64 核下 L2 目录更新与 NoC 事务的全局序不保证，某些场景下 hart 读到 stale L1 行。
- **机理**：Ariane L1 是 write-through（store 直达 L2），但 load 可能命中 stale L1 行（在 L2 目录更新前）。需要一个**全局序屏障**强制所有先前 NoC 事务完成。
- **修复**：silent MMIO-read barrier —— 每个 non-IRQ trap 入口读 UART LSR `0xfff0c2c005`（**uncached** MMIO 读，绕过 L1，经 L1.5→NoC→chipset 往返，强制所有先前 store 全局可见）。零输出、零阻塞。这是 dbg21 能到 shell 的最终 coherency 修复。

> **A7 的注记**：这个"coherency race"的 RTL 根因诊断（一度归咎 `wt_l15_adapter.sv:121 = '0'` 断了 L1 invalidate 路径）**后来被证明是误诊**（见 C4）。barrier 是有效的软件 workaround，但底层 RTL 是否真有 coherency bug，在 07-01 的 `coh_2core`/`coh_64core` sim PASS 后存疑。

### B. 失败的修复尝试（dbg22 / dbg23，记录避免重蹈）

#### B1. dbg22：barrier 扩到 all traps（含 IRQ）→ timer-IRQ livelock 冻在 `[0.000000]`
- **现象**：dbg22 把 silent barrier 从 non-IRQ trap 扩到**所有 trap（含 timer/software 中断）**，boot 冻在 `[0.000000] efi: UEFI not found`（比 dbg21 更早）。
- **根因**：barrier-before-ack。
- **机理**：barrier 在 `sbi_trap_handler` 最顶端跑（在 ack timer 之前）。Linux `[0.000000]` 校准阶段 timer 被立即 arm，barrier 延迟 ack 直到 timer 再次触发 → **紧密中断 livelock** → 冻在最早阶段。
- **结论**：回退到 dbg21 的 non-IRQ gate（只对 ecall 等异常 barrier，不对 IRQ）。

#### B2. dbg23：`csrw 0x701` 禁 L1 D-cache → OpenSBI 入口冻结
- **现象**：dbg23 试图在 `sbi_hart_init` 用 `csrw 0x701, zero` 禁 L1 D-cache（绕过 coherency），bootrom `B68 jump fw=0x80000000` 后 OpenSBI **从未打印 banner**（30 min 静默）。
- **根因**：禁 L1 D-cache 后 OpenSBI 早期执行路径坏。
- **机理**：静态分析说禁 L1 应 pass-through（enable_i 只 gate missunit 分配，不影响 request/response），但实测入口即冻结——禁 cache 路径在 Ariane + OpenPiton L1.5 适配器组合下有未知的早期依赖。
- **结论**：disable-path 死路，放弃，保留 L1 开启。

### C. 64 核运行时挂死（dbg25 → dbg28，当前主战场）

#### C1. DTB `linux,initrd-end` stale → initramfs 截断 → "No working init"（ETXTBSY）
- **现象**：dbg25 长捕获（1800s，扛过 SSH 断）抓到所有短捕获错过的关键行：`Run /bin/sh as init process` → `Starting init: /bin/sh exists but couldn't execute it (error -26)`（ETXTBSY）→ `Kernel panic: No working init`。
- **根因**：`p3_make_opensbi_bundle_image.py` **不自动设** DTB 的 `linux,initrd-start/end`（DTB 原样打包）。DTB 带了**旧 rootfs 的 stale 值** `0x901078a5`，而 v2 rootfs 实际 `0x90000000 + 0x107d9c = 0x90107d9c`，**短了 1271 字节**。
- **机理**：Linux 按 stale `initrd-end` 只解 cpio 到 1271 字节短的位置，**截断 cpio `TRAILER!!!` + 最后一个文件**。解包器没干净收尾，busybox 被留在**写打开**状态 → `execve("/bin/sh")` 返回 `-ETXTBSY`（文本文件忙）→ "No working init"。busybox 本身有效（qemu-riscv64 能跑），失败是截断解包，不是二进制。
- **修复**：DTB `linux,initrd-end` 改 `0x90107d9c`（dbg26）。TODO：改 packer 自动 `initrd-end = initrd_addr + len(initrd)`，杜绝复发。
- **附带纠偏**：这同时证明之前所有"64 核跑过 XSBench / XSBench froze"的 claim 都不成立——boot 一直在 init panic（被短捕获掩盖），从没到 shell。

#### C2. `stop_machine` IPI 死锁（dbg27 决定性证据）⭐ —— 当前真正阻塞
- **现象**：dbg26 initrd 修好后，boot 到 `[32s] clocksource_done_booting` 后**死锁**：`[402s] watchdog: BUG: soft lockup - CPU#0 stuck for 347s! [migration/0]`，栈 `Stopper: multi_cpu_stop <- stop_machine_cpuslocked`。dbg27 加 bootargs 后看到 **64 个 hart 全部 online（`smp: Brought up 1 node, 64 CPUs`），但只有 6 个 `{0,1,3,4,11,12}` 进入 `multi_cpu_stop` 忙等**。
- **根因**：stop_machine 要求所有 online CPU 响应 IPI 进 `multi_cpu_stop`；**58 个 hart 没收到/没响应这个 IPI**，已响应的 6 个永久忙等。
- **机理**：stop_machine 给所有 online CPU 发唤醒 IPI（migration 线程）；58 个 hart 的中断没到 → 它们不进 `multi_cpu_stop` → 已进的 6 个 spin 等 → 无请求超时（见 C6）→ 永久静默挂。SBI ecall 全成功（UART 无 `__sbi_send_ipi_v02` 错误）→ OpenSBI 确实写了 64 个 MSIP，但 58 个 hart 没收到中断信号。
- **修复**：**未解决**——正在判别是 MSIP MMIO 写没到达 CLINT（#1）还是 CLINT→tile 中断层断，还是 ipi_type coherence。dbg28 探针路线（见 E）受阻中。

#### C3. `__do_softirq+0x9e` EPC 被误读为 "timer 崩溃点"（已纠正）
- **现象**：早期 capture 看到 crash `epc=__do_softirq+0x9e`、`cause=0x8000000000000005`，一度解读为"timer 中断遍历损坏的 hrtimer 链表崩溃"。
- **根因（纠正）**：反汇编 `__do_softirq`，EPC `+0x9e` 的前一条是 `csrsi sstatus,2`（开 S-mode 中断），EPC 指向 `sext.w a5,s11`（**纯寄存器操作，不访存，永不 fault**）。
- **机理**：migration 线程在 `multi_cpu_stop` 忙等时，timer 中断照常进来（timer 无辜），中断退出走 `__irq_exit_rcu → __do_softirq`，EPC 落在 softirq 入口（开中断后的下一条）。**这是中断返回地址，不是故障点**。`cause` bit63=1 是"中断"不是"fault"。
- **结论**：纠正了"kernel timer 数据结构损坏"假设。timer 彻底洗清。

#### C4. "L1 coherence 断了"（`wt_l15_adapter.sv:121 = '0'`）误诊（已纠正）⭐
- **现象**：06-26 静态分析推断 `wt_l15_adapter.sv:121 assign l15_invalidate_cacheline = '0` 断了 L1 invalidate 路径，导致 64 核 coherency 违例。
- **根因（纠正）**：`wt_l15_adapter.sv:121` 那行是 **outgoing**（core 主动发起的 invalidate，Ariane 未用），**不是** incoming coherence invalidation。真正的 incoming 路径（`L15_EVICT_REQ → DCACHE_INV_REQ`，`wt_l15_adapter.sv:269-327` + `wt_dcache_missunit.sv:317-354`）完整 wired。
- **机理（证明）**：07-01 写了 printf-free 的 `coh_2core.c` / `coh_64core.c`，在 64-tile Verilator 模型上跑：core 0 plain-store，所有其他 hart 必须看到新值才能 pass。**2 核 PASS、64 核 PASS**（所有 63 reader 看到 core 0 的写）——证明 broadcast L1 invalidation 在 64 核功能正常。之前 `dbg22`/`dbg23` 是在追一个不存在的 bug。
- **结论**：L1 coherence 不是问题。这是这两周最重要的纠偏之一（避免在 RTL 改 L1 snoop 上浪费周）。

#### C5. "kernel timer 数据结构损坏" 误诊（已纠正）
- **现象**：见 C3，crash EPC 在 `__do_softirq` 被当成 timer 链表遍历崩溃。
- **根因（纠正）**：(a) EPC 是中断入口边界不是故障点（C3）；(b) `CONFIG_DEBUG_LIST/SG/PLIST=y` 会抓链表损坏并 WARN，但日志无任何 warning；(c) 失败**间歇**（同 image 有时到 shell 有时挂）→ 确定性软件 bug 必然每次必现 → 不可能是内核 timer 数据损坏。
- **结论**：排除 kernel timer scaling bug。

#### C6. "无请求超时"架构 —— 静默永久挂的放大器（关键发现）
- **现象**：所有失败模式都是**静默永久挂**（boot stall / stop_machine / XSBench freeze），无 trap、无日志、无栈。
- **根因**：`grep -riE "timeout|watchdog"` 在 `tile/l15`、`tile/l2`、`dynamic_node`、`wt_l15_adapter` 全**零命中**（唯一 hit 是 testbench `sim_timeout.sv`——它存在正说明设计能无限期挂）。
- **机理**：L1.5/L2 MSHR 为一个 miss 分配后，**若响应永不返回，MSHR 永久 PENDING**——没有超时来触发 trap 或 retry。所以任何 NoC 响应丢失（中断或数据）都变成静默永久挂，而不是带栈的崩溃。这放大了 C2 的 IPI 死锁（无超时 → migration 永久 spin，不报错）。
- **结论（架构层面）**：这是为什么所有症状都是静默挂。修复方向：要么 RTL 加请求超时，要么软件层加看门狗（dbg27 的 softlockup_panic 就是软件看门狗，把静默挂变成 dump）。

#### C7. 64 线程 XSBench 挂在 "Intializing unionized grid"
- **现象**：07-03 在可靠 shell 上跑 `/root/XSBench -s small -l 100000`（64 线程），过了 nuclide grids init，冻在 "Intializing unionized grid..."（768K 能量网格点的排序合并，重 64 线程并行计算），shell 变无响应。
- **根因**：与 C2 同源——重并行计算触发系统级 IPI/中断/内存子系统的间歇失败，被 C6 的无超时放大成永久挂。
- **机理**：unionized grid init 是 64 线程密集同步 + 共享写，触发 stop_machine 类 IPI 风暴；某个 hart 的 IPI/中断没到 → 卡死。
- **修复**：依赖 C2 的解决（IPI 投递可靠性）。

### D. 仿真 / 工具链 / 环境问题（这两周新搭建/新踩的坑）

#### D1. Verilator 4.014 被 bison 3.8.2 阻塞 → 改用系统 Verilator 5.046
- **现象**：Ariane 自带 Verilator 4.014 编不出来。
- **根因**：bison 3.8.2 不生成 4.014 需要的 `verilog.h`。
- **修复**：放弃 4.014，改用系统 Verilator 5.046（Option B 比 Option A 移植 4.014 更便宜）。三个小修复（无设计 RTL 改动）让 v5 编通（见 D2-D4）。

#### D2. `sims,2.0:1534` `-CFLAGS -lstdc++` → `-LDFLAGS -lstdc++`
- **现象**：v5 编译 `undefined reference to main`。
- **根因**：`-lstdc++` 是**链接器** flag，被错误放在编译 flag（CFLAGS）里。
- **机理**：v5 的 precompiled-header g++ 命令吃到这个 `-lstdc++`，触发一次链接，没 main → 报错。
- **修复**：移到 `-LDFLAGS`。g++ 默认就链 libstdc++，所以也更正确。

#### D3. Verilator 5 需要 `--no-timing`
- **现象**：`%Error-NEEDTIMINGOPT: pc_cmp.tmp.v:802: #20`。
- **根因**：v5 要求显式选项处理 `#delay` 语句（4.014 忽略它们）。
- **修复**：`-vlt_build_args=--no-timing`。

#### D4. Verilator 5 width warnings → `-Wno` 抑制
- **现象**：大量宽度不匹配 warning。
- **根因**：**验证 monitor**（`cmp_l15_messages_mon`、`pc_cmp`、`ciop_iob`）的 benign 宽度问题，非设计 RTL。
- **修复**：`-Wno-WIDTHEXPAND -Wno-WIDTHTRUNC -Wno-WIDTH -Wno-SELRANGE -Wno-ASCRANGE -Wno-WIDTHCONCAT`。

#### D5. 64-tile Verilator 编译墙（21 MB root part -Os 编 50+ min）
- **现象**：64-tile flat 设计巨大，Verilator elaborated root 的 `__11` 部分（21 MB / 261K 行）在 g++ `-Os`（verilated.mk 默认）下编 50-80+ min 不完成。
- **根因**：`-Os` size-optimization 在超大 single unsplittable block 上极慢；`--output-split 500` 生成 26289 个小文件仍有一个慢 root part。
- **修复**：`--hierarchical`（每模块编一次，~1450 文件而非 26000 flat 副本，64 tile 共享一份）+ `-CFLAGS -O0`（覆盖 verilated.mk `-Os`，跳过 size-opt，13 min 编完）。两者都必需。

#### D6. `make -j` unlimited → WSL OOM
- **现象**：不限并发 `make -j` spawn 数千 cc1plus → WSL 内存泄露 → 用户被迫 kill 整个 WSL。
- **修复**：`sims,2.0:1580` 改 `make -j 16`（有界）。

#### D7. `printf` 在 Verilator 永久挂（UART unmodeled）
- **现象**：调 `printf` 的 coherency diag 在 Verilator 永久 spin，core 不 trap。
- **根因**：C 运行时 `printbuf`（`syscalls.c`）每字符前轮询 UART LSR bit 5（THRE）；Verilator testbench **不模型 UART**，poll 永远看不到 THRE → 死循环。
- **修复**：Verilator 下的 coherency/功能 diag 必须 **printf-free**，只用 `pass()`/`fail()` 信号（good/bad trap 读 `status.log`）。

#### D8. `coh_ipi64` monitor `$display` 抑制破坏 Verilog 结构
- **现象**：想抑制 `cmp_l15_messages_mon` 的高量 `$display`（364 个/tile × 64 tile）加速 sim，但 sed 注释、python 正则都破坏了 Verilog（空 label、贪婪吞 begin/end）。
- **修复**：局部 `do_print_stage_TILE0 = 1'b0`（只关一个 monitor section），完整抑制未解决（接受 sim 慢）。

#### D9. SSH 复杂命令 exit 255
- **现象**：含 `sudo`/`pkill`/复杂 quoting 的 SSH 命令随机 drop（exit 255）。
- **根因**：`pkill -f "timeout.*cat /dev/ttyUSB"` 会自匹配 SSH 命令串，杀掉自己的 session；复杂 quoting 在 Windows 跳板解析出错。
- **修复**：拆成简单单动作命令；UART 用 `dialout` 组免 sudo；用 detached `cat` + `timeout` 抓取。

#### D10. SD 卡写卡 sudo / 盘符确认
- **现象**：`/dev/sdc` 是 `root:disk`，illya 不在 disk 组；Kingston Multi-Reader 暴露多个 0B 空槽。
- **修复**：写前 `lsblk` 二次确认非零盘（`SIZE>0, TYPE=disk, TRAN=usb, RM=1, MODEL=Multi-Reader`）；用 `echo 'pw' | sudo -S` 写；readback `sha256sum` 校验前 256MB。

### E. dbg28 OpenSBI MSIP 探针受挫（一连串误判，已查清）

#### E1. 在 `openpiton.c` final_init 加 MSIP 探针 → OpenSBI 连 banner 都不出
- **现象**：dbg28 在 `openpiton.c final_init` 加 MSIP 写+回读探针（判 C2 的 MSIP 写到达），bootrom 跳 OpenSBI 后**静默挂死**，banner 都没出。
- **根因**：probe 给 openpiton.c 加了 `riscv_io.h`/`sbi_console.h`/`riscv_asm.h` 等 includes + final_init 代码，**破坏了 openpiton.c 的编译**（虽然 make 没报错）。
- **机理**：includes 改变了 openpiton.o 的代码生成/布局，间接破坏了 OpenSBI 早期启动（banner 之前）。probe 在 final_init（banner 后），banner 没出 = probe 没执行到，所以不是 probe 逻辑错，是 includes 的编译期副作用。
- **修复**：改加到 `aclint_mswi.c`（已 include `riscv_io.h`，不引入新 includes）= dbg28c。但 dbg28c 也挂（见 E2/E3 调查）。

#### E2. 误判 "dbg21 用 gcc 17 远程编" → 纠正：dbg21 就是本地 gcc 11.4
- **现象**：dbg28 挂后，看到 dbg21 fw 和我编的 fw 从 byte 151 就不同，且 prebuilt.elf `.comment` 显示 gcc 17.0 → 推断 dbg21 用 gcc 17（远程）。
- **根因（纠正）**：(a) `find` 全系统无 `riscv64-unknown-linux-gnu-gcc`（p3_prepare 默认）；(b) wiki `2026-06.md:703` 铁证"Rebuilt OpenSBI locally with `riscv64-linux-gnu-` (gcc 11.4)"；(c) dbg21 `_start` 反汇编和我编的（gcc 11.4）**完全一致**（`jal 0x800007a8` 等）。
- **结论**：dbg21 和 dbg28 用**同一个 gcc（本地 riscv64-linux-gnu 11.4）**。gcc 不是问题。byte 151 的 8 字节差异是 `sbi_trap.c` 的 `coherency_barrier_count` 变量（dbg21 后源码改动），良性。

#### E3. 误判 "忘了禁 PIE" → 纠正：Makefile 早有 -fno-pie hack
- **现象**：怀疑 dbg28 是 PIE build（PIE 自重定位失败，见上周报根因 #2）。
- **根因（纠正）**：今天编的 fw `Type=EXEC`（non-PIE），entry 0x80000000。Makefile 有 `-fno-pie`/`-no-pie` hack（dbg21 时为修 PIE 加的，持久保留）。
- **结论**：dbg28 是 non-PIE，和 dbg21 一样。PIE 不是问题。

#### E1-E3 综合结论
dbg28c（probe 在 aclint_mswi.c，non-PIE，gcc 11.4 = dbg21 全同配置）**仍挂** → 不是 gcc/PIE/probe 位置。当前嫌疑：今天编的 fw 含 dbg21 后的源码改动（`sbi_trap.c` barrier 等）某个组合破坏启动，或 probe 即使在 aclint_mswi.c 也有编译期副作用。**待 dbg28b（无 probe）隔离**。
- **教训**：先查 wiki 再下结论——gcc/PIE 的答案 wiki 里早有，浪费了多轮 SD/XVC 迭代。

## 四、方法论亮点

1. **板上分层证据链**：编程→DONE bit→UART→bootrom→DDR→SD→OpenSBI→Linux→SMP→shell，逐层证明不跳步；每层独立证据才下结论。
2. **bootargs 让挂有声**（dbg27）：`softlockup_panic/panic_on_warn/rcu_cpu_stall_timeout/watchdog_thresh` 把 C6 的"静默永久挂"变成 soft lockup dump + 栈——零综合（只改 DTB）抓到 C2 的 stop_machine 死锁铁证。
3. **静态优先**：反汇编 `__do_softirq`（解开 C3）、源码审查 SBI-IPI 全链路（排除代码 bug）、`grep timeout`（发现 C6）——减少昂贵的 SD/XVC 迭代。
4. **printf-free Verilator diag**（D7）：`coh_2core`/`coh_64core` 只用 good/bad trap 信号，绕过 UART unmodeled，拿到 C4 的 coherency PASS 证据。
5. **R1 wiki 同步**：每个根因/发现/纠偏即时 devlog + commit + push（两周 25+ 次），保证可追溯、可纠错。
6. **诚实纠偏**：主动纠正 L1 coherence（C4）、timer 损坏（C5）、gcc/PIE（E2/E3）等误诊，记录在 devlog 不掩盖——这两周最有价值的方法论进步。

## 七、对 P0–P4 路线图的影响

- **P3（8×8 / 64 核）**：核心打通到 Linux shell，但 **stop_machine IPI 死锁阻塞 XSBench**。这是 64 核规模才暴露的中断投递可靠性问题（2 核/单核不复现；`coh_2core`/`coh_64core` 简单 store-load 都过，但 Linux 并发 stop_machine IPI 风暴下 58/64 丢失）。
- **P4（1024 核）**：IPI 投递可靠性是关键障碍——64 核就有 58/64 不响应，1024 核会更严重。必须先解决 CLINT MSIP 经 NoC→chipset 的中断投递可靠性（或换中断机制），才能往更大规模推。
- **Quicksilver**：需可靠的多核 IPI + 收敛才能跑并行 benchmark。当前阻塞在 IPI 死锁。
