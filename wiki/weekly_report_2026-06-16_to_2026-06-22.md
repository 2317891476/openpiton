## 一、本周目标

在 Versal VP1902 (P3) 上实现 **8×8 / 64 核 OpenPiton+Ariane 的 OpenSBI→Linux 启动**。本周一的起点是："bootrom 全程正常，但跳转到 OpenSBI 后 UART 静默（OpenSBI 在入口处 fault/hang）"。本周的目标是逐层定位并清除 OpenSBI coldboot 路径上的每一个门槛，让 64 核首次跑到 OpenSBI banner 并向 Linux 推进。

## 二、本周核心成果（一句话）

**从"OpenSBI 入口静默"推进到"OpenSBI v1.8 横幅打印"——64 核 OpenPiton 有史以来第一次跑到 OpenSBI banner**，并连续静态定位+修复了 **5 个非平凡根因**（其中 2 个是 OpenPiton 平台层 64 核扩展的"沉默陷阱"）。

## 四、技术深度：5 个根因详解

### 根因 #1：Ariane 缺 `mhpmevent` CSR（非法指令 trap）
- OpenSBI `mstatus_init` 复位 `mhpmevent3..31`，其 gate `mhpm_mask` 由探测 `mhpmcounter`（计数 CSR）填充。**Ariane 实现了 `mhpmcounter` 但不实现 `mhpmevent`（事件选择器）**；OpenSBI 假定二者共存 → 写 `mhpmevent4` → 非法指令 trap → 静默挂死。
- 修复：`sbi_hart_mhpm_mask()` 返回 0 → 跳过所有 `mhpmevent` 写。

### 根因 #2：OpenSBI PIE 自重定位在 P3 失败
- 该版本 OpenSBI 在顶层 Makefile 硬编码 `-fPIE -pie`，且 apt gcc 默认 `--enable-default-pie`，所以 `FW_PIC=n` 无效。
- PIE 二进制在 P3 上 GOT 指针停留链接地址（`0x500xx`），`sbi_pmu_init` 解引用 → load/store access fault。
- 修复：CFLAGS/ASFLAGS `-fno-pie`、ELFFLAGS `-no-pie`、`fw_base.ldS` 基址硬编码 `0x80000000` → 产出 `Type=EXEC`、无运行时重定位。

### 根因 #3：`openpiton.c` 平台 override 硬编码 3 核（64 核沉默陷阱）⭐
- P3 DTB 根节点 `compatible="openpiton,cva6platform"` 触发加载 `platform/generic/openhwgroup/openpiton.c`，它把 generic 的 timer/ipi/irqchip 换成自己的**静态实现，全部按 3 核配置**（`OPENPITON_DEFAULT_HART_COUNT=3`）。
- `aclint_mtimer_cold_init` 只给 hart 0/1/2 的 scratch 设了 mtimer 指针；coldboot 若是 hart≥3（`fw_boot_hart=-1` 抽签非确定），`aclint_mtimer_warm_init` 拿到 NULL → 返回 `SBI_ENODEV` → `sbi_timer_init` 返回错误 → `sbi_hart_hang()` → **冻在 C/D 之间**。
- 这解释了 dbg3(能过)/dbg4(卡住) 的非确定性差异（抽奖运气）。
- 修复：`HART_COUNT=64` + `plic.context_map` 从 3 项扩到 64 项 `[i]={2i,2i+1}`（对照 DTB `interrupts-extended` 校验）。

### 根因 #4：`plic_data = plic` 的 432 字节柔性数组结构体拷贝溢出（反汇编证明）⭐
- `openpiton_early_init` 里 `struct plic_data plic_data = plic;` —— `context_map` 是柔性数组 `s16 [][2]`（`sizeof` 不含），但 **GCC 对柔性数组结构体赋值按源对象实际大小拷贝**：静态 `plic` 带 64 项 context_map 初始化器，实际 432 字节，所以拷贝 432 字节进一个 224 字节栈帧，溢出覆盖保存的 `s2/s1/s0/ra`（sp+192/200/208/216），写入的正是 context_map[2..7]（`4,5,…,15`）。函数返回 `ret` 载入垃圾 `ra=0x000f000e000d000c` → 取指错误。
- 这是 64 核扩展（context_map 从 3 项→64 项）**新引发的二阶 bug**：3 项时拷贝很小不命中 ra。
- 修复：去掉栈 local，`fdt_parse_plic(fdt, &plic, ...)` 直接解析进静态 `plic`。

### 根因 #5：PMP memrange 切碎超过 16 entry（hart isolation）⭐
- banner 后 `sbi_hart_protection_configure` 配 PMP。`sbi_domain_root_add_memrange(addr,size,align,…)` 把每个区域按 `align` 切成 power-of-2 块。设备 align 太小（`0x1000`）→ mtimer 切 8 块、mswi 切 4 块、plic 切 3 块… 合计 ~18 > Ariane 的 16 个 PMP entry → "insufficient PMP entries"。
- 修复方案：mtimer `MTIMER_REGION_ALIGN 0x1000→0x4000`（8→2 块）、mswi memrange align→`0x4000`（4→1 块），合计降到 ~9 < 16。

## 五、方法论亮点

1. **静态优先，减少 SD 卡迭代**：用户多次要求"先静态排查再烧卡"。本周大量根因通过**纯源码分析 + 反汇编**定位（根因 #3/#4/#5 都是静态推出），避免了昂贵的 SD/XVC 迭代。特别是根因 #4 用反汇编直接证明 432 字节拷贝溢出，**比模拟器更确定**。
2. **R1 wiki 同步规则严格执行**：每个根因/修复/构建都即时写进 `wiki/devlog/2026-06.md` 并 commit+push（本周 12+ 次 wiki 提交），保证可追溯。
3. **ILA + UART 标记双管齐下**：ILA 证明 coldboot 进 OpenSBI 区；UART 逐级标记（OSBI1/A-H/T0-T4/e1-e5）精确定位冻结点。

## 附录：各 dbg 构建详解

以下按时间顺序列出本周每个 OpenSBI 调试构建（dbg → dbg12）的**改动、目的、板上结果和结论**，完整还原排查链路。

### dbg — 首次加仪器：OSBI1 + P3TRAP

- **改动**：在 `sbi_init.c` init_coldboot 入口加 `p3_puts("OSBI1")`（直接写 ns16550 UART `0xfff0c2c000`，无 console 依赖）；在 `sbi_trap.c` sbi_trap_handler 入口加 `P3TRAP cause=… epc=… tval=…` dump。OpenSBI 以 `FW_PIC=y`（PIE）构建，复用现有 Image/DTB/rootfs 打包。
- **目的**：确认 bootrom 跳转后 OpenSBI 是否到达 `sbi_init`；若 trap，拿到 cause/epc/tval 定位。
- **结果**：UART 打出 `OSBI1`（**OpenSBI 到达 sbi_init，跳转+早期执行 OK**），随后 `P3TRAP cause=0x2 epc=0x80012bfa tval=0x32459073`（非法指令）。`addr2line`：epc 在 `csr_write_num`；tval 反汇编 = `csrw mhpmevent4,a1`（CSR 0x324）。
- **结论**：**根因 #1** — Ariane 实现 `mhpmcounter` 但不实现 `mhpmevent`（事件选择器），OpenSBI 写 `mhpmevent4` → 非法指令 trap。

### dbg2 — mhpm_mask 修复 + 静态扫描

- **改动**：`sbi_hart_mhpm_mask()` 返回 0 → `mstatus_init` 跳过所有 `mhpmevent` 写。保留 OSBI1/P3TRAP。同时静态扫描了 DT（`p3_opensbi_64hart.dts`）和 CSR 路径，排除 DT/CSR 不匹配。
- **目的**：验证 mhpm_mask 修复消除 trap；若仍 spin，静态排查 DT/CSR。
- **结果**：`OSBI1` 后 **`P3TRAP count = 0`**（trap 消除，修复有效），但 UART 冻结在 `OSBI1` >40 分钟（**spin 而非 trap**）。DT/CSR 扫描干净（CLINT/PLIC/UART/SD 地址匹配，无虚假 AIA/IMSIC）。
- **结论**：mhpm trap 已解决；post-OSBI1 spin 是运行时问题（MMIO 挂死或 secondary 等待），需要进一步定位。构建 dbg3 加 A-H 逐级标记。

### dbg3 — A–H 逐级标记：定位 spin 到 pmu_init 的 PIE 重定位失败

- **改动**：在 init_coldboot 每步后加标记：`A`=hsm_init、`B`=wake_coldboot_harts、`C`=hart_init、`D`=timer_init、`E`=platform_early_init、`F`=pmu_init、`G`=dbtr_init、`H`=banner 前。
- **目的**：一次启动定位最后一个出现的标记 = 冻结点。
- **结果**：`OSBI1 A B C D E` 然后 `P3TRAP` 洪水（cause=4 load fault / cause=6 store fault，tval=`0x500xx`），全部在 `sbi_pmu_init`（`sbi_pmu.c:1226 sbi_platform_ptr(scratch)`）。**`0x500xx` 是 platform 结构体的链接地址**（应在重定位后变成 `0x800500xx`）。
- **结论**：**根因 #2** — OpenSBI PIE 自重定位在 P3 上失败，GOT 指针停留链接地址 `0x0xxxxxxx`。Makefile 硬编码 `-fPIE -pie`，gcc 默认 `--enable-default-pie`，`FW_PIC=n` 无效。

### dbg4 — 非 PIE 构建 + 清洁重编程

- **改动**：Makefile CFLAGS `-fno-pie`、ASFLAGS `-fno-pie`、ELFFLAGS `-no-pie`（覆盖 gcc 默认 pie）；`fw_base.ldS` 基址硬编码 `. = 0x80000000`（FW_TEXT_START 未传播到 .ldS 预处理）。产出 `Type=EXEC`、entry `0x80000000`、无运行时重定位。
- **目的**：消除 PIE 重定位依赖，让 OpenSBI 以绝对地址运行。
- **结果（首次）**：UART 打到 "B69 C" 后冻结，**无 OSBI1**（疑似回归）。后经分析 + **清洁重编程**（完整 PDI 重烧），得到正确序列：`OSBI1 A B C` 然后冻结（**无 D**）。ILA 佐证：一个 secondary 核停在 `sbi_hsm_hart_wait`（正常等待），证明 coldboot 到了 wake_coldboot_harts(B) 之后、timer_init(D) 之前。
- **结论**：非 PIE 链接正确（EXEC@0x80000000）；"B69 C" 是抓取毛刺。新门槛：**coldboot 冻结在 `sbi_timer_init`（C/D 之间）**。

### dbg5 — timer_init 精确标记 + CLINT 探针（构建后被静态分析取代）

- **改动**：在 `sbi_timer_init` 加 `T0`（入口）、`Tmt=<mtime 值>`（直接读 CLINT mtime `0xfff102bff8`）、`ThasTIME`、`T1`(platform_timer_init 前)、`T2`(后)、`T3`(warm_init 前)、`T4`(后)。
- **目的**：精确定位 timer_init 内部的冻结点 + 测试 CLINT MMIO 可达性。
- **结果**：**未上板测试**——在准备烧卡前，用户要求"先静态排查"。静态走通 `sbi_timer_init → sbi_platform_timer_init → aclint_mtimer_cold_init`，发现 `openpiton.c` 硬编码 `hart_count=3` → coldboot≥hart3 时 `aclint_mtimer_warm_init` 返回 ENODEV → hang。**根因 #3 在烧卡前静态定位**。
- **结论**：timer_init 的 CLINT 探针标记被合并进 dbg6（连同 64 核修复）。

### dbg6 — 64 核 openpiton.c 修复 + timer 标记：timer_init 通过，新 trap

- **改动**：`OPENPITON_DEFAULT_HART_COUNT 3→64`；`plic.context_map` 从 3 项扩到 64 项 `[i]={2i,2i+1}`；保留 mhpm_mask + OSBI1/P3TRAP/A-H + dbg5 的 timer 标记。
- **目的**：验证 3 核硬编码修复（根因 #3）消除 timer_init 冻结。
- **结果**：`OSBI1 A B C T0 Tmt=0000000004cccfa2 T1 T2 T3 T4 D` —— **CLINT mtime 读取成功**（有效递增值）、**timer_init 全部完成**（`D` 打出）。timer_init 冻结彻底解决。但 D 之后出现新 trap：`P3TRAP cause=1 epc=000f000e000d000c`，`sbi_trap_error: hart4`，寄存器被 `0x0004…0x000f` 顺序模式污染。
- **结论**：根因 #3 修复有效（timer_init 通过）；新门槛 = hart4 stack-corruption trap。

### dbg7 — coldboot hartid + warm-boot 标记：修正"从核"误判

- **改动**：加 `CB<hartid>`（coldboot 入口打印 hartid）；secondary 进 warmboot 打 `W<hartid>`、过 hsm_init 打 `Wa`、过 hart_init 打 `Wh`（gated hartid<8）。
- **目的**：确定 coldboot 是哪个核；hart4 是 coldboot 还是从核。
- **结果**：`OSBI1 CB1 A B W7 C Tmt=… D → trap on hart1`。**关键发现**：coldboot 是 **hart 1**（`_boot_lottery` 抽签非确定，不总是 hart 0），**trap 在 coldboot 自己身上**（CB1 = trap hart1），不是从核。`0x0004…0x000f` 模式与 coldboot hartid 无关（dbg6 hart4 / dbg7 hart1 模式相同）= 固定写入。
- **结论**：修正了 dbg6 的"从核"误判；trap 是 coldboot 在 `platform_early_init`（D/E 之间）。模式 `4,5,…,15` = plic `context_map[2..7]` 的值。

### dbg8 — 去掉栈 local plic_data（432B 溢出修复）：到达 banner ⭐

- **改动**：去掉 `openpiton_early_init` 里的 `struct plic_data plic_data = plic;`（反汇编证明：GCC 对柔性数组结构体赋值拷贝 432 字节，溢出 224 字节栈帧，覆盖保存的 s0/s1/ra）。改为 `fdt_parse_plic(fdt, &plic, …)` 直接解析进静态 plic。加 e1-e5 标记在 openpiton_early_init 各步前后。
- **目的**：验证 432 字节结构体拷贝溢出修复（根因 #4）。
- **结果**：`OSBI1 CB1 A B C Tmt=… D e1 e2 e3 e4 e5 E F G H OpenSBI v1.8` —— **platform_early_init 全部完成（e1-e5），一路到 OpenSBI v1.8 横幅！** 64 核首次到达 banner。但 banner 后 `error: insufficient PMP entries / init_coldboot: hart isolation configure failed (error -1)`。
- **结论**：根因 #4 修复有效；coldboot 到达 banner（里程碑）。新门槛 = PMP 不足（hart isolation）。

### dbg9 — 强制 old PMP（禁用 SMEPMP）

- **改动**：`sbi_hart_pmp_init` 始终注册 `pmp_protection`（old PMP，rating 100），不再注册 `epmp_protection`（SMEPMP，rating 200）；`epmp_protection` 标 `__attribute__((unused))`。old PMP 每 region 1 个 PMP entry（SMEPMP 用 2 个）。
- **目的**：排除 SMEPMP 双倍消耗 PMP entry 的可能。
- **结果**：**仍然 "insufficient PMP entries"** —— 说明 root domain 确实 >16 个 memregion，不仅仅是 SMEPMP 的 2 倍。
- **结论**：PMP 耗尽的根因不是 SMEPMP，而是 memregion 数量本身 >16。需进一步排查 memregion 来源。

### dbg10 — PMP region dump（被静态分析取代）

- **改动**：在 `sbi_hart_oldpmp_configure` 循环里加 per-region 打印（`P<idx> b=<base> o=<order>`），列出每个 memregion。
- **目的**：板上列出所有 memregion，找出 >16 的原因。
- **结果**：**未上板测试**——用户要求"直接静态列出"。静态走通 `sbi_domain_root_add_memrange` 的 power-of-2 切分算法，发现 align=0x1000 导致 mtimer 切 8 块、mswi 切 4 块……合计 ~18 > 16。**根因 #5 在烧卡前静态定位**。
- **结论**：region dump 标记被合并进 dbg11（连同 align 修复）。

### dbg11 — align 修复 + region dump：`_start` 回归

- **改动**：`MTIMER_REGION_ALIGN 0x1000→0x4000`（mtimer 8→2 块）；mswi memrange align `0x1000→0x4000`（4→1 块）；保留 region dump 打印 + p3 helpers。
- **目的**：验证 align 修复让 PMP 总数降到 ~9 < 16。
- **结果**：**两次重编程（dbg11, dbg11b）均卡在 bootrom→OpenSBI 交接处**——bootrom 全程正常（"releasing harts / jump fw=0x80000000 / jump dtb=0x88000000"），但 OpenSBI **从未打出 OSBI1**。capture 冻结数分钟。非瞬时（可复现）。
- **结论**：dbg11 引入了 `_start` 回归。dbg11 fw binary 的 `_start[0:256]`、大小（270048B）、符号与 dbg9 **完全相同**，但 dbg9 能到 banner 而 dbg11 卡死。疑似调试打印的 p3 helpers 改变了二进制布局，触发了 64 核 `_start` 的布局敏感性一致性/时序竞争。

### dbg12 — 仅 align 修复（去掉打印）：隔离回归（进行中）

- **改动**：去掉 `sbi_hart_pmp.c` 里的 region dump 打印 + p3 helpers（恢复 dbg9 的 sbi_hart_pmp.c），保留 align 修复 + old-PMP + 无 plic_data local。
- **目的**：隔离 dbg11 的 `_start` 回归——是打印引起的布局偏移，还是 align 修复本身。
- **结果**：**待上板验证**。若 dbg12 到达 banner + 过 PMP → 打印是元凶，align 修复有效。若 dbg12 也卡 `_start` → align 修复或 64 核 `_start` 竞争需单独治理。
