# 周报：64 核 OpenPiton OpenSBI 启动调试（2026-06-16 ~ 2026-06-22）

## 一、本周目标

在 Versal VP1902 (P3) 上实现 **8×8 / 64 核 OpenPiton+Ariane 的 OpenSBI→Linux 启动**。本周一的起点是："bootrom 全程正常，但跳转到 OpenSBI 后 UART 静默（OpenSBI 在入口处 fault/hang）"。本周的目标是逐层定位并清除 OpenSBI coldboot 路径上的每一个门槛，让 64 核首次跑到 OpenSBI banner 并向 Linux 推进。

## 二、本周核心成果（一句话）

**从"OpenSBI 入口静默"推进到"OpenSBI v1.8 横幅打印"——64 核 OpenPiton 有史以来第一次跑到 OpenSBI banner**，并连续静态定位+修复了 **5 个非平凡根因**（其中 2 个是 OpenPiton 平台层 64 核扩展的"沉默陷阱"）。

## 四、技术深度：5 个根因详解

### 根因 #1：Ariane 缺 `mhpmevent` CSR（非法指令 trap）
- OpenSBI `mstatus_init` 复位 `mhpmevent3..31`，其 gate `mhpm_mask` 由探测 `mhpmcounter`（计数 CSR）填充。**Ariane 实现了 `mhpmcounter` 但不实现 `mhpmevent`（事件选择器）**；OpenSBI 假定二者共存 → 写 `mhpmevent4` → 非法指令 trap → 静默挂死。
- 修复：`sbi_hart_mhpm_mask()` 返回 0 → 跳过所有 `mhpmevent` 写。

### 根因 #2：OpenSBI PIE 自重定位在 P3 失败
- 该版本 OpenSBI 在顶层 Makefile 硬编码 `-fPIE -pie`，且 apt gcc 默认 `--enable-default-pie`，所以 `FW_PIC=n` 无效。
- PIE 二进制在 P3 上 GOT 指针停留链接地址（`0x500xx`），`sbi_pmu_init` 解引用 → load/store access fault。
- 修复：CFLAGS/ASFLAGS `-fno-pie`、ELFFLAGS `-no-pie`、`fw_base.ldS` 基址硬编码 `0x80000000` → 产出 `Type=EXEC`、无运行时重定位。

### 根因 #3：`openpiton.c` 平台 override 硬编码 3 核（64 核沉默陷阱）⭐
- P3 DTB 根节点 `compatible="openpiton,cva6platform"` 触发加载 `platform/generic/openhwgroup/openpiton.c`，它把 generic 的 timer/ipi/irqchip 换成自己的**静态实现，全部按 3 核配置**（`OPENPITON_DEFAULT_HART_COUNT=3`）。
- `aclint_mtimer_cold_init` 只给 hart 0/1/2 的 scratch 设了 mtimer 指针；coldboot 若是 hart≥3（`fw_boot_hart=-1` 抽签非确定），`aclint_mtimer_warm_init` 拿到 NULL → 返回 `SBI_ENODEV` → `sbi_timer_init` 返回错误 → `sbi_hart_hang()` → **冻在 C/D 之间**。
- 这解释了 dbg3(能过)/dbg4(卡住) 的非确定性差异（抽奖运气）。
- 修复：`HART_COUNT=64` + `plic.context_map` 从 3 项扩到 64 项 `[i]={2i,2i+1}`（对照 DTB `interrupts-extended` 校验）。

### 根因 #4：`plic_data = plic` 的 432 字节柔性数组结构体拷贝溢出（反汇编证明）⭐
- `openpiton_early_init` 里 `struct plic_data plic_data = plic;` —— `context_map` 是柔性数组 `s16 [][2]`（`sizeof` 不含），但 **GCC 对柔性数组结构体赋值按源对象实际大小拷贝**：静态 `plic` 带 64 项 context_map 初始化器，实际 432 字节，所以拷贝 432 字节进一个 224 字节栈帧，溢出覆盖保存的 `s2/s1/s0/ra`（sp+192/200/208/216），写入的正是 context_map[2..7]（`4,5,…,15`）。函数返回 `ret` 载入垃圾 `ra=0x000f000e000d000c` → 取指错误。
- 这是 64 核扩展（context_map 从 3 项→64 项）**新引发的二阶 bug**：3 项时拷贝很小不命中 ra。
- 修复：去掉栈 local，`fdt_parse_plic(fdt, &plic, ...)` 直接解析进静态 `plic`。

### 根因 #5：PMP memrange 切碎超过 16 entry（hart isolation）⭐
- banner 后 `sbi_hart_protection_configure` 配 PMP。`sbi_domain_root_add_memrange(addr,size,align,…)` 把每个区域按 `align` 切成 power-of-2 块。设备 align 太小（`0x1000`）→ mtimer 切 8 块、mswi 切 4 块、plic 切 3 块… 合计 ~18 > Ariane 的 16 个 PMP entry → "insufficient PMP entries"。
- 修复方案：mtimer `MTIMER_REGION_ALIGN 0x1000→0x4000`（8→2 块）、mswi memrange align→`0x4000`（4→1 块），合计降到 ~9 < 16。

## 五、方法论亮点

1. **静态优先，减少 SD 卡迭代**：用户多次要求"先静态排查再烧卡"。本周大量根因通过**纯源码分析 + 反汇编**定位（根因 #3/#4/#5 都是静态推出），避免了昂贵的 SD/XVC 迭代。特别是根因 #4 用反汇编直接证明 432 字节拷贝溢出，**比模拟器更确定**。
2. **R1 wiki 同步规则严格执行**：每个根因/修复/构建都即时写进 `wiki/devlog/2026-06.md` 并 commit+push（本周 12+ 次 wiki 提交），保证可追溯。
3. **ILA + UART 标记双管齐下**：ILA 证明 coldboot 进 OpenSBI 区；UART 逐级标记（OSBI1/A-H/T0-T4/e1-e5）精确定位冻结点。
